# Журнал решений проекта

## Назначение

Этот документ фиксирует ключевые решения проекта.

Его нужно обновлять после каждого важного решения, чтобы при обрыве чата можно было восстановить логику проекта.

## Решение 1. Сначала база, потом подбор

Решение:

Сначала строим базу профессий, специальностей и направлений. Вопросы, подбор и рекомендации временно не делаем.

Причина:

Без проверенной базы система будет придумывать направления и выдавать ненадёжные рекомендации.

Следствие:

До отдельного решения не создавать:

1. вопросы;
2. подбор;
3. пользовательские рекомендации;
4. пользовательский бизнес-план.

## Решение 2. Безопасная база важнее полной сырой базы

Решение:

Первый рабочий вариант должен строиться на безопасной базе, а не на полном сыром списке всех профессий.

Причина:

Полная сырая база быстро становится грязной: дубли, широкие названия, устаревшие профессии, направления без бюджета, направления без рынка, совпадения по словам без совпадения смысла.

Следствие:

Направление должно попадать в рабочую базу только после минимальной проверки.

## Решение 3. Соцконтракт — один режим, но не вся система

Решение:

Система должна поддерживать бизнес-планы под соцконтракт, но не ограничиваться соцконтрактом.

Причина:

Пользователь может хотеть обычный бизнес-план, план с бюджетом больше 350 000 рублей или план под другой источник денег.

Следствие:

В ТЗ нужно заложить разные режимы бизнес-плана.

## Решение 4. Бюджет клиента должен быть гибким

Решение:

Пользователь должен иметь возможность указать бюджет:

1. точной суммой;
2. верхней границей;
3. диапазоном;
4. неизвестным бюджетом.

Примеры:

1. `1 200 000 рублей`;
2. `до 3 000 000 рублей`;
3. `от 500 000 до 1 500 000 рублей`.

Причина:

Направления должны подбираться под реальный стартовый капитал, а не только под лимит соцконтракта.

Следствие:

В базе направления должны быть стартовые траты, нормальный запуск, расширенный запуск и сравнение с бюджетом клиента.

## Решение 5. Финансовая аналитика не должна сочиняться

Решение:

Расчёты, структура бизнес-плана, финансовые показатели и правила оценки должны опираться на проверенные источники.

Причина:

Проект не должен выдумывать финансовую методику.

Следствие:

Если для расчёта нет источника или данных, нужно писать `нужно подтвердить источником` или `недостаточно данных`.

## Решение 6. Человек не должен быть обязательной частью клиентского процесса

Решение:

Клиентский продукт должен быть автоматизирован.

Причина:

Если каждый бизнес-план требует ручной работы человека, экономика продукта не сойдётся.

Следствие:

Ручная проверка допустима только как внутренняя работа по наполнению и улучшению базы, но не как обязательный шаг клиентской услуги.

## Решение 7. ИИ и инструменты должны быть заменяемыми

Решение:

Нельзя жёстко привязывать систему к Codex, MiMo, DeepSeek или другому названию.

Причина:

Сегодня один инструмент лучше собирает данные, завтра другой. Сегодня один ИИ лучше анализирует, завтра другой.

Следствие:

В ТЗ нужно описать роли:

1. сборщик информации;
2. аналитик;
3. составитель бизнес-плана;
4. проверяющий;
5. собеседник с клиентом.

Каждая роль должна иметь возможность работать через командную строку или API.

## Решение 8. Сборщик информации не обязан анализировать

Решение:

Сборщик информации может только ходить по источникам и сохранять факты.

Причина:

Это дешевле и легче контролировать. Анализ можно делать отдельной ролью.

Следствие:

Факты и выводы нужно хранить отдельно.

## Решение 9. История источников обязательна

Решение:

Для каждой цены, факта, вывода и расчёта нужно хранить источник и дату.

Причина:

Цены меняются, источники устаревают, выводы нужно перепроверять.

Следствие:

В базе нужны поля источников, даты сбора, города, версии расчёта и даты следующего обновления.

## Решение 10. Новые специальности добавляются через кандидатов

Решение:

Новая специальность не должна сразу попадать в рабочую базу.

Путь:

1. найден кандидат;
2. собраны источники;
3. собраны цены услуг;
4. собраны цены оборудования;
5. проверены налоги и ограничения;
6. посчитаны расходы;
7. посчитана точка безубыточности;
8. присвоен статус.

Следствие:

Нужен отдельный документ про добавление новых специальностей.
