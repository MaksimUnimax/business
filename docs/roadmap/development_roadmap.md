# План работ по разработке

## Назначение

Этот документ фиксирует порядок разработки.

Он нужен, чтобы не перескакивать к подбору, вопросам или бизнес-планам до готовности базы и ТЗ.

## Текущий этап

Текущий этап:

`документы для разработки`

До этого уже сделано:

1. собраны источники;
2. построена связка источников;
3. проверена связка источников;
4. создана черновая структура базы;
5. создана черновая база на 10 направлений;
6. создан снимок текущего состояния базы;
7. создан документ-основание для ТЗ.

## Этап 1. Контекст и управление проектом

Цель:

Сделать так, чтобы проект можно было восстановить после обрыва чата или смены исполнителя.

Документы:

1. `docs/project_context/current_chat_context.md`
2. `docs/project_context/decision_log.md`
3. `docs/roadmap/development_roadmap.md`

Готово, когда:

1. есть текущий контекст;
2. есть журнал решений;
3. есть план работ;
4. всё сохранено в Git.

## Этап 2. Полное ТЗ

Цель:

Описать, что должна делать система и чего она не должна делать.

Документ:

1. `docs/requirements/full_tz.md`

В ТЗ должны быть:

1. цель системы;
2. пользователь;
3. режимы бизнес-плана;
4. бюджет клиента;
5. база направлений;
6. источники;
7. финансовая аналитика;
8. добавление новых специальностей;
9. замена ИИ и инструментов;
10. ограничения;
11. критерии готовности.

Готово, когда:

1. ТЗ не содержит выдуманных финансовых методик;
2. спорные места помечены как `нужно подтвердить источником`;
3. ТЗ сохранено в Git.

## Этап 3. Описание базы направлений

Цель:

Описать структуру базы так, чтобы по ней можно было разрабатывать систему.

Документ:

1. `docs/requirements/direction_database_spec.md`

Нужно описать:

1. направление;
2. профессию;
3. специальность;
4. услугу;
5. вариант запуска;
6. бюджет;
7. расходы;
8. источники;
9. статусы;
10. обновление цен;
11. связь фактов и выводов.

Готово, когда:

1. понятно, какие поля нужны;
2. понятно, какие поля обязательны;
3. понятно, какие статусы бывают;
4. понятно, что нельзя показывать пользователю.

## Этап 4. Правила финансовой аналитики

Цель:

Описать, как считать бизнес-показатели без выдумок.

Документ:

1. `docs/requirements/financial_analysis_rules.md`

Нужно описать:

1. стартовые расходы;
2. текущие расходы;
3. расходы на один заказ;
4. цену услуги;
5. точку безубыточности;
6. движение денег;
7. сценарии;
8. окупаемость;
9. денежный запас;
10. источники для расчётов.

Готово, когда:

1. каждая формула имеет источник или пометку `нужно подтвердить источником`;
2. система не должна придумывать цифры;
3. если данных нет, результат должен быть `недостаточно данных`.

## Этап 5. Правила источников и обновления цен

Цель:

Описать, откуда брать данные и как понимать, что они устарели.

Документ:

1. `docs/requirements/source_and_price_rules.md`

Нужно описать:

1. источники профессий;
2. источники цен услуг;
3. источники цен оборудования;
4. источники правил налогов;
5. источники правил соцконтракта;
6. дату сбора;
7. срок актуальности;
8. дату следующего обновления;
9. что делать, если источник недоступен.

Готово, когда:

1. у каждой цифры есть источник;
2. у каждой цены есть дата;
3. есть правило устаревания цены;
4. есть правило замены источника.

## Этап 6. Правила добавления новых специальностей

Цель:

Описать, как новая специальность становится кандидатом и потом попадает в базу.

Документ:

1. `docs/requirements/new_specialty_intake_rules.md`

Нужно описать путь:

1. найден кандидат;
2. собраны источники;
3. собраны цены;
4. собраны расходы;
5. проверены ограничения;
6. посчитана точка безубыточности;
7. присвоен статус;
8. принято решение.

Готово, когда:

1. новая специальность не может попасть в рабочую базу без данных;
2. есть статусы кандидата;
3. есть причины отказа или отложения.

## Этап 7. Правила смены ИИ и инструментов

Цель:

Описать, как менять Codex, MiMo, DeepSeek и другие инструменты без переделки системы.

Документ:

1. `docs/requirements/ai_tool_roles.md`

Нужно описать роли:

1. сборщик информации;
2. аналитик;
3. составитель бизнес-плана;
4. проверяющий;
5. собеседник с клиентом.

Нужно описать способы запуска:

1. через командную строку;
2. через API.

Готово, когда:

1. каждая роль имеет вход;
2. каждая роль имеет выход;
3. роль можно заменить;
4. система не зависит от одного названия инструмента.

## Этап 8. Формат бизнес-плана

Цель:

Описать, из каких блоков будет собираться бизнес-план.

Документ:

1. `docs/requirements/business_plan_output_spec.md`

Нужно описать:

1. бизнес-план под соцконтракт;
2. обычный бизнес-план;
3. бизнес-план с большим бюджетом;
4. смету;
5. финансовую часть;
6. источники;
7. приложения;
8. что делать, если данных не хватает.

Готово, когда:

1. понятно, какие блоки есть;
2. понятно, какие данные нужны для каждого блока;
3. понятно, какие блоки отличаются для соцконтракта и обычного плана.

## Этап 9. Проверки готовности

Цель:

Описать, как понять, что база и документы готовы для разработки.

Документ:

1. `docs/requirements/acceptance_checks.md`

Нужно описать:

1. проверки базы;
2. проверки источников;
3. проверки цен;
4. проверки расчётов;
5. проверки бизнес-плана;
6. проверки замены ИИ;
7. проверки, что система не сочиняет.

Готово, когда:

1. есть понятный список проверок;
2. можно остановить разработку, если проверка не проходит.

## Этап 10. Только после документов — разработка

Разработку подбора, вопросов, рекомендаций и бизнес-планов начинать только после документов:

1. полное ТЗ;
2. описание базы;
3. правила финансовой аналитики;
4. правила источников;
5. правила добавления новых специальностей;
6. правила смены ИИ;
7. формат бизнес-плана;
8. проверки готовности.

До этого не делать пользовательский подбор.
