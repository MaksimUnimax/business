# Правила смены ИИ и инструментов

## 1. Назначение документа

Этот документ описывает, как будущая система должна работать с ИИ, инструментами, командной строкой, API и заменяемыми ролями.

Документ нужен для разработки.

Этот документ не является кодом.

Этот документ не запускает ИИ.

Этот документ не настраивает API.

Этот документ не запускает командную строку.

Этот документ фиксирует архитектурное правило: система не должна зависеть от одного конкретного ИИ или одного конкретного инструмента.

## 2. Главный принцип

Система не должна быть жёстко привязана к Codex, MiMo, DeepSeek или любому другому названию.

Названия конкретных инструментов могут использоваться только как текущий вариант, но не как вечное правило.

Сегодня один инструмент может быть лучше для сбора информации.

Завтра другой инструмент может быть лучше для сбора информации.

Сегодня один ИИ может быть лучше для аналитики.

Завтра другой ИИ может быть лучше для аналитики.

Система должна позволять заменять исполнителей без переписывания всей базы, всех документов и всей логики.

## 3. Почему это важно

Причины:

1. инструменты быстро меняются;
2. качество ИИ может меняться;
3. стоимость ИИ может меняться;
4. одни инструменты лучше работают через командную строку;
5. другие инструменты лучше работают через API;
6. сегодня может быть доступен браузер у Codex;
7. завтра может появиться хороший браузер у MiMo;
8. один ИИ может плохо анализировать финансы;
9. другой ИИ может лучше анализировать финансы;
10. один источник может перестать работать;
11. один инструмент может попасть в ограничения;
12. экономику продукта нельзя привязывать к дорогому или нестабильному исполнителю.

## 4. Что система не должна делать

Система не должна:

1. жёстко вшивать Codex как единственного сборщика;
2. жёстко вшивать MiMo как единственного аналитика;
3. жёстко вшивать DeepSeek как единственного аналитика;
4. считать, что сборщик всегда анализирует;
5. считать, что аналитик всегда собирает источники;
6. смешивать роли;
7. хранить важную логику только в свободном тексте;
8. зависеть от одного API;
9. зависеть от одной командной строки;
10. зависеть от одного браузера;
11. зависеть от одного промпта;
12. терять историю источников при замене ИИ;
13. терять факты при замене аналитика;
14. менять структуру данных при каждой смене инструмента.

## 5. Главные роли системы

В системе должны быть роли.

Роль — это не конкретный инструмент.

Роль — это задача, которую можно выполнить разными инструментами.

Минимальные роли:

1. сборщик информации;
2. аналитик;
3. составитель бизнес-плана;
4. проверяющий;
5. собеседник с клиентом;
6. составитель базы;
7. обновлятор цен;
8. контролёр источников;
9. исполнитель документации;
10. технический исполнитель.

## 6. Сборщик информации

Сборщик информации отвечает за сбор фактов из источников.

Сборщик может работать:

1. через браузер;
2. через командную строку;
3. через API;
4. через заранее заданные ссылки;
5. через внутренние файлы.

Сборщик должен возвращать факты, источники и ошибки.

Сборщик не обязан делать финансовый анализ.

Сборщик не должен придумывать выводы.

Сборщик не должен обещать прибыль.

Сборщик не должен решать, подходит ли направление пользователю, если это не его роль.

## 7. Текущий вариант сборщика

Текущий черновой вариант:

1. Codex + браузер может собирать информацию по ссылкам;
2. Codex может ходить по Авито, Ozon или другим открытым страницам, если доступ безопасен;
3. Codex не должен анализировать финансы, если задача только сбор;
4. Codex не должен обходить капчу;
5. Codex не должен логиниться без отдельного разрешения;
6. Codex не должен собирать контакты;
7. Codex не должен делать массовый сбор.

Этот вариант не является вечным.

Если появится MiMo с браузером или другой инструмент, его можно поставить на роль сборщика.

## 8. Аналитик

Аналитик отвечает за выводы и расчёты на основе фактов.

Аналитик должен получать:

1. направление;
2. город;
3. бюджет клиента;
4. режим бизнес-плана;
5. факты;
6. источники;
7. цены;
8. расходы;
9. ограничения;
10. правила расчётов.

Аналитик должен возвращать:

1. расчёты;
2. выводы;
3. недостающие данные;
4. риски;
5. уровень доверия;
6. ссылки на факты;
7. статус расчёта.

Аналитик не должен придумывать цифры.

Если данных нет, аналитик должен писать:

`недостаточно данных`

Если методика не подтверждена, аналитик должен писать:

`нужно подтвердить источником`

## 9. Текущий вариант аналитика

Текущий черновой вариант:

1. MiMo может делать аналитику;
2. MiMo может получать факты, собранные другим инструментом;
3. MiMo может считать или описывать расчёты, если данные есть;
4. MiMo не должен собирать рынок, если роль сборщика назначена другому инструменту;
5. MiMo не должен придумывать недостающие данные.

Этот вариант не является вечным.

Если анализ MiMo будет плохой, можно заменить его на DeepSeek или другой ИИ.

Если API-модель окажется лучше, можно использовать API-модель.

Если модель через командную строку окажется дешевле, можно использовать командную строку.

## 10. Составитель бизнес-плана

Составитель бизнес-плана отвечает за сборку документа бизнес-плана.

Он должен брать:

1. направление из базы;
2. бюджет клиента;
3. режим плана;
4. факты;
5. источники;
6. расчёты;
7. ограничения;
8. шаблон бизнес-плана;
9. недостающие данные;
10. риски.

Он не должен придумывать цифры.

Он не должен обещать одобрение соцконтракта.

Он не должен обещать прибыль.

Если данных не хватает, он должен явно писать:

`недостаточно данных`

## 11. Проверяющий

Проверяющий отвечает за контроль качества.

Проверяющий должен искать:

1. неподтверждённые цифры;
2. отсутствующие источники;
3. устаревшие цены;
4. смешивание фактов и выводов;
5. скрытые допущения;
6. юридические риски;
7. неверный режим бизнес-плана;
8. попытку обещать прибыль;
9. попытку обещать соцконтракт;
10. использование черновика как готовой рекомендации.

Проверяющий тоже должен быть заменяемым.

## 12. Собеседник с клиентом

Собеседник с клиентом отвечает за общение с пользователем.

Он должен:

1. задавать понятные вопросы;
2. принимать бюджет точной суммой;
3. принимать бюджет верхней границей;
4. принимать бюджет диапазоном;
5. принимать неизвестный бюджет;
6. объяснять простым языком;
7. не обещать прибыль;
8. не обещать соцконтракт;
9. передавать данные структурно;
10. не придумывать факты.

Собеседник с клиентом может быть отдельным ИИ.

Собеседник с клиентом может отличаться от аналитика.

Собеседник с клиентом может отличаться от сборщика.

## 13. Составитель базы

Составитель базы отвечает за создание или обновление записей базы.

Он должен работать только по правилам базы.

Он не должен добавлять направление без источников.

Он не должен добавлять направление только потому, что его предложил ИИ.

Он должен соблюдать статусы:

1. кандидат;
2. черновик;
3. не хватает данных;
4. не хватает источника;
5. нужно обновить цены;
6. можно использовать внутри;
7. можно использовать в пользовательском процессе;
8. отклонено;
9. заблокировано по юридической причине;
10. архив.

## 14. Обновлятор цен

Обновлятор цен отвечает за обновление цен услуг, оборудования, расходов и рыночных сигналов.

Он должен:

1. получать список нужных цен;
2. ходить только по разрешённым источникам;
3. сохранять дату;
4. сохранять ссылку;
5. сохранять город;
6. сохранять ошибку, если источник недоступен;
7. не обходить капчу;
8. не логиниться без разрешения;
9. не считать старую цену свежей.

Обновлятор может быть отдельным инструментом.

## 15. Контролёр источников

Контролёр источников отвечает за качество источников.

Он должен проверять:

1. источник официальный или нет;
2. источник первичный или зеркало;
3. источник свежий или устарел;
4. источник доступен или заблокирован;
5. источник подходит для типа данных;
6. источник подтверждает факт или только даёт сигнал;
7. есть ли противоречия с другими источниками.

Контролёр источников может быть отдельной ролью или частью проверяющего.

## 16. Исполнитель документации

Исполнитель документации отвечает за создание документов в Git.

Он должен:

1. брать текст из prompt;
2. не сочинять содержание;
3. не добавлять свои требования;
4. не менять смысл;
5. не менять базу;
6. не менять код;
7. делать commit и push, если это указано в задаче;
8. возвращать отчёт.

Эта роль сейчас часто выполняется MiMo.

## 17. Технический исполнитель

Технический исполнитель отвечает за код, тесты, миграции и технические изменения.

Эта роль включается только когда проект переходит к разработке.

Сейчас эта роль не должна создавать подбор, вопросы, рекомендации или бизнес-планы.

Перед техническими изменениями нужен backup.

Для изменений с базой или состоянием нужен отдельный backup.

## 18. Командная строка

Любая роль может работать через командную строку, если это поддерживает инструмент.

Командная строка подходит для:

1. работы в repo;
2. создания файлов;
3. запуска скриптов;
4. запуска локальных моделей;
5. запуска CLI-инструментов;
6. проверки статуса Git;
7. фиксации документов;
8. запуска тестов, когда это разрешено.

Правило:

Командная строка — это способ запуска, а не конкретный ИИ.

## 19. API

Любая роль может работать через API, если это поддерживает инструмент.

API подходит для:

1. внешних моделей;
2. внутренних сервисов;
3. аналитики;
4. генерации текста;
5. проверки данных;
6. подготовки бизнес-плана;
7. работы с клиентским интерфейсом.

Правило:

API — это способ запуска, а не конкретный ИИ.

## 20. Браузер

Браузер может быть нужен сборщику информации.

Браузер подходит для:

1. открытых страниц;
2. точечных проверок;
3. ручных и полуавтоматических проверок;
4. сбора видимых фактов;
5. сохранения текстовых снимков;
6. сохранения даты и ссылки.

Браузер не должен использоваться для:

1. обхода капчи;
2. обхода логина;
3. сбора контактов;
4. массового сбора;
5. скрытого обхода защиты;
6. нарушения правил площадки.

## 21. Текущая схема ролей

Текущая возможная схема:

1. сборщик информации: Codex + браузер;
2. аналитик: MiMo;
3. исполнитель документации: MiMo;
4. проверка GitHub: ChatGPT;
5. собеседник с клиентом: будущий отдельный ИИ;
6. составитель бизнес-плана: будет определён позже;
7. проверяющий: будет определён позже.

Эта схема временная.

Она не должна быть жёстко зашита в архитектуру.

## 22. Возможная будущая схема

В будущем возможна другая схема:

1. сборщик информации: MiMo + браузер;
2. аналитик: DeepSeek;
3. составитель бизнес-плана: отдельная API-модель;
4. собеседник с клиентом: другая API-модель;
5. проверяющий: локальный CLI-инструмент;
6. обновлятор цен: отдельный сборщик;
7. контролёр источников: отдельная роль.

Система должна позволять такую замену.

## 23. Общий контракт роли

Каждая роль должна иметь общий контракт.

Контракт роли — это:

1. вход;
2. выход;
3. разрешённые действия;
4. запрещённые действия;
5. формат ошибок;
6. формат отчёта;
7. история выполнения;
8. источник данных;
9. версия задания;
10. версия результата.

Без контракта роль нельзя безопасно заменить.

## 24. Вход роли

Вход роли должен быть структурным.

Пример:

```json
{
  "role_task": {
    "task_id": "",
    "role": "",
    "input_data": {},
    "allowed_actions": [],
    "forbidden_actions": [],
    "required_output_format": "",
    "context_refs": [],
    "source_refs": [],
    "created_at": ""
  }
}
```

Правило:

1. вход не должен быть только свободным текстом;
2. вход должен указывать роль;
3. вход должен указывать запреты;
4. вход должен указывать ожидаемый выход;
5. вход должен ссылаться на источники и документы.

## 25. Выход роли

Выход роли должен быть структурным.

Пример:

```json
{
  "role_result": {
    "task_id": "",
    "role": "",
    "status": "completed | partial | failed | stopped",
    "outputs": {},
    "facts_created": [],
    "conclusions_created": [],
    "sources_used": [],
    "missing_data": [],
    "errors": [],
    "warnings": [],
    "confidence": "low | medium | high | unknown",
    "created_at": ""
  }
}
```

Правило:

1. результат должен иметь статус;
2. ошибки должны быть видны;
3. недостающие данные должны быть видны;
4. источники должны быть видны;
5. факты и выводы должны быть разделены.

## 26. Формат ошибки

Ошибка должна быть структурной.

Пример:

```json
{
  "role_error": {
    "task_id": "",
    "role": "",
    "error_type": "missing_data | source_blocked | source_unavailable | insufficient_permissions | invalid_input | tool_failed | unknown",
    "message": "",
    "recoverable": true,
    "next_step": "",
    "created_at": ""
  }
}
```

Правило:

1. ошибка не должна теряться;
2. ошибка должна объяснять причину;
3. если можно продолжить, нужно указать следующий шаг;
4. если нельзя продолжить, нужно остановиться.

## 27. Смена исполнителя

Смена исполнителя должна быть возможна без изменения бизнес-логики.

Пример:

1. было: Codex собирает цены услуг;
2. стало: MiMo с браузером собирает цены услуги.

Если вход и выход роли одинаковые, система не должна ломаться.

Меняется только исполнитель роли.

## 28. Смена ИИ для аналитики

Аналитик должен быть заменяемым.

Пример:

1. было: MiMo анализирует факты;
2. стало: DeepSeek анализирует факты;
3. позже: другая модель анализирует факты.

Требование:

1. факты остаются;
2. источники остаются;
3. выводы можно пересчитать;
4. старая аналитика не удаляется без причины;
5. новая аналитика хранит модель и дату.

## 29. Смена ИИ для клиента

Собеседник с клиентом должен быть заменяемым.

Пример:

1. один ИИ общается с клиентом;
2. другой ИИ анализирует;
3. третий ИИ составляет бизнес-план.

Требование:

1. клиентский ИИ не должен придумывать факты;
2. клиентский ИИ должен передавать данные структурно;
3. клиентский ИИ не должен напрямую менять базу;
4. клиентский ИИ не должен обещать прибыль;
5. клиентский ИИ не должен обещать соцконтракт.

## 30. Смена способа запуска

Одна и та же роль может работать:

1. через командную строку;
2. через API;
3. через браузер;
4. через внутренний сервис.

Пример:

1. сегодня аналитик работает через командную строку;
2. завтра аналитик работает через API;
3. послезавтра аналитик работает через локальный сервис.

Система должна хранить способ запуска в истории.

## 31. Настройки ролей

В будущем должна быть настройка ролей.

Пример структуры:

```json
{
  "role_config": {
    "collector": {
      "enabled": true,
      "provider": "codex",
      "run_mode": "cli",
      "browser_enabled": true
    },
    "analyst": {
      "enabled": true,
      "provider": "mimo",
      "run_mode": "cli"
    },
    "business_plan_writer": {
      "enabled": true,
      "provider": "unknown",
      "run_mode": "api"
    },
    "client_chat": {
      "enabled": true,
      "provider": "unknown",
      "run_mode": "api"
    }
  }
}
```

Это пример будущей структуры.

Сейчас код не создаётся.

## 32. Версионирование ролей

Нужно хранить версию роли и исполнителя.

Структура:

```json
{
  "role_execution": {
    "execution_id": "",
    "role": "",
    "provider": "",
    "tool_name": "",
    "model_name": "",
    "run_mode": "cli | api | browser | internal",
    "prompt_version": "",
    "config_version": "",
    "started_at": "",
    "finished_at": "",
    "status": ""
  }
}
```

Правило:

1. нужно знать, кто выполнил задачу;
2. нужно знать, какой инструмент использовался;
3. нужно знать, какая модель использовалась;
4. нужно знать, какой был prompt или версия задания;
5. нужно знать дату выполнения.

## 33. История выполнения

Каждое выполнение роли должно иметь историю.

История нужна, чтобы:

1. восстановить контекст;
2. проверить источник ошибки;
3. пересчитать выводы;
4. заменить исполнителя;
5. сравнить качество разных ИИ;
6. доказать, что данные не придуманы.

## 34. Сравнение исполнителей

В будущем система должна позволять сравнивать исполнителей.

Пример:

1. один аналитик дал вывод;
2. другой аналитик дал другой вывод;
3. система хранит оба вывода;
4. проверяющий сравнивает выводы;
5. итоговый статус показывает противоречие.

Структура:

```json
{
  "role_comparison": {
    "comparison_id": "",
    "role": "",
    "executions": [],
    "differences": [],
    "resolution_status": "unresolved | resolved | needs_more_data",
    "notes": ""
  }
}
```

## 35. Что делать при плохом качестве ИИ

Если ИИ даёт плохой результат, система должна позволять:

1. заменить ИИ;
2. сменить prompt;
3. сменить роль;
4. сменить способ запуска;
5. снизить доверие к выводу;
6. отправить задачу другому исполнителю;
7. сохранить ошибку;
8. не ломать факты и источники.

Плохой вывод нельзя silently принимать как истину.

## 36. Что делать при недоступности ИИ

Если ИИ недоступен:

1. сохранить ошибку;
2. поставить статус задачи `failed` или `partial`;
3. не выдавать выдуманный результат;
4. попробовать другой разрешённый исполнитель, если это предусмотрено;
5. если замены нет, остановиться и показать причину.

## 37. Что делать при дорогом ИИ

Если ИИ дорогой, система должна позволять:

1. использовать дешёвого сборщика;
2. использовать дорогую модель только для сложной аналитики;
3. разделять сбор и анализ;
4. кэшировать факты;
5. пересчитывать выводы без повторного сбора фактов;
6. менять модель аналитика.

Это важно для экономики продукта.

## 38. Разделение сбора и анализа

Сбор и анализ должны быть разделены.

Причина:

1. сбор может быть дешёвым;
2. анализ может быть дорогим;
3. сборщик может ошибиться в выводах;
4. аналитик может не уметь хорошо работать с браузером;
5. факты должны сохраняться независимо от вывода;
6. выводы можно пересчитать позже.

Текущий принцип:

1. Codex + браузер может собирать факты;
2. MiMo может анализировать факты;
3. позже обе роли можно заменить.

## 39. Разделение клиента и аналитики

ИИ, который общается с клиентом, не обязан быть аналитиком.

Причина:

1. хороший собеседник не всегда хороший аналитик;
2. хороший аналитик не всегда хороший собеседник;
3. клиентский ИИ должен говорить просто;
4. аналитик должен работать строго с фактами;
5. бизнес-план может составлять отдельная роль.

## 40. Разделение аналитики и бизнес-плана

Аналитик и составитель бизнес-плана могут быть разными ролями.

Аналитик отвечает за расчёты и выводы.

Составитель бизнес-плана отвечает за оформление результата.

Если составитель бизнес-плана видит, что расчётов не хватает, он не должен придумывать.

Он должен написать:

`недостаточно данных`

## 41. Запрет на свободную замену без контракта

Нельзя просто заменить один инструмент на другой, если новый инструмент не возвращает нужную структуру.

Перед заменой нужно проверить:

1. вход понимается;
2. выход структурный;
3. ошибки видны;
4. источники сохраняются;
5. факты не смешиваются с выводами;
6. запреты соблюдаются;
7. результат можно проверить.

## 42. Требования к сборщику

Сборщик должен уметь возвращать:

1. источники;
2. факты;
3. ошибки;
4. недостающие данные;
5. дату сбора;
6. город;
7. инструмент;
8. модель, если она использовалась.

Сборщик не должен:

1. обходить капчу;
2. логиниться без разрешения;
3. собирать контакты;
4. делать массовый сбор без ограничений;
5. придумывать цены;
6. делать финансовый вывод, если это не его роль.

## 43. Требования к аналитику

Аналитик должен уметь возвращать:

1. расчёты;
2. выводы;
3. статус расчёта;
4. недостающие данные;
5. риски;
6. ссылки на факты;
7. уровень доверия;
8. версию расчёта.

Аналитик не должен:

1. придумывать факты;
2. придумывать цены;
3. обещать прибыль;
4. обещать соцконтракт;
5. использовать устаревшие цены как свежие;
6. скрывать нехватку данных.

## 44. Требования к составителю бизнес-плана

Составитель бизнес-плана должен уметь:

1. собрать текст из блоков;
2. использовать факты;
3. использовать расчёты;
4. использовать источники;
5. указать недостающие данные;
6. различать соцконтракт и обычный бизнес-план;
7. не обещать результат;
8. не подставлять недостающие цифры.

## 45. Требования к проверяющему

Проверяющий должен уметь находить:

1. неподтверждённые числа;
2. отсутствие источников;
3. устаревшие цены;
4. скрытые допущения;
5. смешивание фактов и выводов;
6. нарушения правил НПД;
7. нарушения правил соцконтракта;
8. обещания прибыли;
9. обещания одобрения;
10. использование черновика как финального результата.

## 46. Требования к собеседнику с клиентом

Собеседник с клиентом должен уметь:

1. принять бюджет точной суммой;
2. принять бюджет верхней границей;
3. принять бюджет диапазоном;
4. принять неизвестный бюджет;
5. объяснять простыми словами;
6. передавать данные структурно;
7. не менять базу напрямую;
8. не придумывать факты;
9. не обещать прибыль;
10. не обещать одобрение соцконтракта.

## 47. Бюджет клиента

Система должна поддерживать бюджет клиента во всех ролях.

Пользователь может указать бюджет:

1. точной суммой: `1 200 000 рублей`;
2. верхней границей: `до 3 000 000 рублей`;
3. диапазоном: `от 500 000 до 1 500 000 рублей`;
4. неизвестным бюджетом.

Структура:

```json
{
  "budget_input_type": "exact | max | range | unknown",
  "budget_min_rub": null,
  "budget_max_rub": null,
  "budget_exact_rub": null,
  "budget_source": "user_input",
  "budget_purpose": "social_contract | own_money | grant | loan | mixed | unknown"
}
```

## 48. Факты и выводы при смене ИИ

При смене ИИ факты должны оставаться.

Выводы можно пересчитать.

Правило:

1. старые факты не удаляются;
2. новые выводы ссылаются на факты;
3. старые выводы можно архивировать;
4. противоречия нужно хранить;
5. модель и дата вывода должны храниться.

## 49. Источники при смене ИИ

При смене ИИ источники должны оставаться.

Новый ИИ не должен терять:

1. ссылки;
2. даты;
3. город;
4. тип источника;
5. уровень доверия;
6. историю сбора;
7. ошибки источников;
8. снимки, если они есть.

## 50. Prompt как заменяемый элемент

Prompt или задание для роли должно быть заменяемым.

Нельзя хранить всю логику только в одном prompt.

Логика должна быть описана в документах:

1. полное ТЗ;
2. описание базы;
3. правила финансовой аналитики;
4. правила источников;
5. правила добавления специальностей;
6. правила смены ИИ;
7. формат бизнес-плана;
8. проверки готовности.

Prompt должен ссылаться на документы или включать нужный текст дословно, если исполнитель не должен сочинять.

## 51. Настройки без переписывания кода

В будущем система должна иметь настройки, которые позволяют менять:

1. сборщика информации;
2. аналитика;
3. составителя бизнес-плана;
4. проверяющего;
5. собеседника с клиентом;
6. способ запуска;
7. модель;
8. prompt;
9. источники;
10. режимы безопасности.

Смена настройки не должна требовать переписывания всей системы.

## 52. Запреты безопасности

Любая роль должна соблюдать запреты:

1. не обходить капчу;
2. не обходить логин;
3. не собирать контакты;
4. не делать массовый сбор без ограничений;
5. не использовать чужие учётные записи;
6. не скрывать ошибки;
7. не придумывать данные;
8. не обещать прибыль;
9. не обещать соцконтракт;
10. не показывать черновик как финальный результат.

## 53. Когда можно заменить инструмент

Инструмент можно заменить, если:

1. новый инструмент понимает вход роли;
2. новый инструмент возвращает нужный выход;
3. новый инструмент сохраняет источники;
4. новый инструмент сохраняет ошибки;
5. новый инструмент соблюдает запреты;
6. новый инструмент дешевле, лучше или доступнее;
7. замена не ломает базу;
8. замена не ломает историю.

## 54. Когда нельзя заменить инструмент

Инструмент нельзя заменить, если:

1. он не возвращает структурный результат;
2. он теряет источники;
3. он смешивает факты и выводы;
4. он придумывает цифры;
5. он нарушает запреты безопасности;
6. он требует ручного человека в клиентском процессе;
7. он ломает текущую базу;
8. он не позволяет проверить результат.

## 55. Проверка нового инструмента

Перед использованием нового инструмента нужно проверить:

1. может ли он выполнить роль;
2. может ли он вернуть структурный результат;
3. сохраняет ли он источники;
4. сохраняет ли он ошибки;
5. не придумывает ли данные;
6. соблюдает ли запреты;
7. можно ли заменить им старый инструмент;
8. что делать при ошибке.

## 56. Минимальный отчёт роли

Каждая роль должна возвращать отчёт.

Минимальный отчёт:

1. роль;
2. инструмент;
3. модель;
4. способ запуска;
5. статус;
6. входные данные;
7. результат;
8. источники;
9. ошибки;
10. недостающие данные;
11. дата;
12. следующий шаг.
