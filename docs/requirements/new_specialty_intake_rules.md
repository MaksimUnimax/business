# Правила добавления новых специальностей

## 1. Назначение документа

Этот документ описывает, как новая профессия, специальность, услуга или направление может попасть в базу.

Документ нужен для разработки.

Этот документ не является кодом.

Этот документ не создаёт новые направления.

Этот документ не запускает сбор рынка.

Этот документ не запускает Авито, Ozon или другие площадки.

Этот документ фиксирует правила, чтобы система не добавляла в рабочую базу мусор, случайные идеи или направления, которые предложил ИИ без доказательств.

## 2. Главный принцип

Новая специальность не должна сразу попадать в рабочую базу.

Сначала она должна стать кандидатом.

Кандидат должен пройти:

1. проверку смысла;
2. проверку источников;
3. проверку услуг;
4. проверку налогов;
5. проверку ограничений;
6. проверку соцконтракта, если режим соцконтракт;
7. сбор цен услуг;
8. сбор цен оборудования;
9. сбор стартовых расходов;
10. сбор текущих расходов;
11. сбор расходов на заказ;
12. расчёт точки безубыточности, если данных хватает;
13. проверку качества источников;
14. присвоение статуса.

До прохождения этих шагов кандидат не должен использоваться в пользовательском процессе.

## 3. Что система не должна делать

Система не должна:

1. добавлять специальность в рабочую базу только потому, что её предложил ИИ;
2. добавлять специальность без источников;
3. добавлять специальность без понятных услуг;
4. добавлять специальность без проверки НПД или ИП;
5. добавлять специальность без проверки соцконтракта, если нужен режим соцконтракта;
6. добавлять специальность без стартовых расходов;
7. добавлять специальность без цен услуг;
8. добавлять специальность без источников оборудования;
9. добавлять специальность без статуса;
10. показывать кандидата пользователю как готовую рекомендацию;
11. делать бизнес-план по кандидату без данных;
12. придумывать недостающие цифры;
13. скрывать, что данных не хватает.

Если данных не хватает, писать:

`недостаточно данных`

Если источник не подтверждён, писать:

`нужно подтвердить источником`

## 4. Термины

## 4.1. Профессия

Профессия — общий род деятельности.

Примеры:

1. парикмахер;
2. швея;
3. сборщик мебели;
4. репетитор;
5. мастер ремонта техники.

## 4.2. Специальность

Специальность — более узкая область внутри профессии.

Примеры:

1. мастер по мужским стрижкам;
2. мастер по ремонту одежды;
3. мастер по ремонту стиральных машин;
4. репетитор по математике;
5. мастер по уходу за животными.

## 4.3. Услуга

Услуга — то, что реально покупает клиент.

Примеры:

1. стрижка;
2. маникюр;
3. ремонт молнии;
4. сборка шкафа;
5. урок английского;
6. выгул собаки.

## 4.4. Направление

Направление — рабочая единица базы, на основе которой можно в будущем делать подбор и бизнес-план.

Направление связывает:

1. профессию;
2. специальность;
3. услуги;
4. вариант запуска;
5. бюджет;
6. ограничения;
7. источники;
8. расчёты.

## 4.5. Кандидат

Кандидат — профессия, специальность, услуга или направление, которое найдено, но ещё не прошло проверку.

Кандидат не равен рабочему направлению.

Кандидат нельзя использовать для пользовательской рекомендации.

## 5. Откуда может появиться кандидат

Кандидат может появиться из разных источников.

Возможные источники кандидата:

1. классификатор;
2. профессиональный стандарт;
3. рыночный сигнал;
4. список услуг;
5. запрос пользователя;
6. внутренняя идея проекта;
7. найденный пробел в базе;
8. вручную заданная ссылка;
9. анализ конкурентов;
10. будущий автоматический мониторинг.

Правило:

Источник появления кандидата должен быть сохранён.

Если кандидат появился из запроса пользователя или предложения ИИ, это не делает его проверенным.

## 6. Структура кандидата

Кандидат должен храниться структурно.

Пример:

```json
{
  "candidate_key": "",
  "title_ru": "",
  "candidate_type": "profession | specialty | service | direction | launch_variant | unknown",
  "candidate_source": "",
  "found_at": "",
  "found_by_role": "",
  "found_by_tool": "",
  "status": "new | collecting_sources | needs_data | needs_source | needs_market_data | needs_price_data | needs_legal_check | needs_social_contract_check | ready_for_internal_review | accepted_to_draft | rejected | archived",
  "profession_hypothesis": "",
  "specialty_hypotheses": [],
  "service_hypotheses": [],
  "launch_variant_hypotheses": [],
  "city_or_region_scope": "",
  "required_checks": [],
  "collected_sources": [],
  "collected_facts": [],
  "missing_data": [],
  "risks": [],
  "decision": null,
  "decision_reason": "",
  "notes": ""
}
```

## 7. Ключ кандидата

Ключ кандидата должен быть стабильным.

Требования:

1. латиница;
2. маленькие буквы;
3. слова через подчёркивание;
4. без случайных чисел, если можно обойтись без них;
5. не привязывать к городу;
6. не привязывать к бюджету;
7. не менять без причины.

Пример:

`photo_video_services_candidate`

Если кандидат позже становится направлением, ключ направления должен быть отдельным и стабильным.

## 8. Статусы кандидата

Минимальные статусы кандидата:

1. `new` — только найден;
2. `collecting_sources` — идёт сбор источников;
3. `needs_data` — не хватает данных;
4. `needs_source` — не хватает источников;
5. `needs_market_data` — не хватает рыночных данных;
6. `needs_price_data` — не хватает цен;
7. `needs_legal_check` — нужна правовая и налоговая проверка;
8. `needs_social_contract_check` — нужна проверка соцконтракта;
9. `needs_financial_inputs` — не хватает финансовых входных данных;
10. `ready_for_internal_review` — готов для внутренней проверки;
11. `accepted_to_draft` — можно перенести в черновую базу;
12. `accepted_to_working_base` — можно перенести в рабочую базу;
13. `ready_for_user_flow` — можно использовать в пользовательском процессе;
14. `rejected` — отклонён;
15. `archived` — убран в архив.

Статус `ready_for_user_flow` нельзя ставить без прохождения проверок качества.

## 9. Жизненный путь кандидата

Путь кандидата:

1. найден кандидат;
2. создана карточка кандидата;
3. сохранён источник появления;
4. проверено, нет ли дубля в базе;
5. собраны источники профессии;
6. собраны источники специальности;
7. собраны возможные услуги;
8. собраны источники услуг;
9. проверены ограничения НПД;
10. проверены ограничения ИП;
11. проверены ограничения соцконтракта, если нужен режим соцконтракта;
12. собраны цены услуг;
13. собраны цены оборудования;
14. собраны стартовые расходы;
15. собраны текущие расходы;
16. собраны расходы на заказ;
17. собраны рыночные сигналы;
18. посчитаны финансовые входные данные;
19. посчитана точка безубыточности, если данных хватает;
20. определены риски;
21. присвоен статус;
22. кандидат принят, отложен или отклонён.

## 10. Проверка дублей

Перед добавлением кандидата нужно проверить, нет ли уже такого направления.

Проверять нужно:

1. ключ;
2. русское название;
3. профессию;
4. специальность;
5. услуги;
6. синонимы;
7. похожие названия;
8. существующие черновые направления;
9. отложенные направления;
10. архивные направления.

Если кандидат похож на существующее направление, нужно не создавать новое направление сразу, а создать связь или пометку `possible_duplicate`.

Структура:

```json
{
  "duplicate_check": {
    "checked_at": "",
    "possible_duplicates": [],
    "duplicate_status": "no_duplicate | possible_duplicate | duplicate | unknown",
    "reason": "",
    "notes": ""
  }
}
```

## 11. Проверка смысла

Кандидат должен быть понятен по смыслу.

Нужно ответить:

1. что это за деятельность;
2. что именно продаётся;
3. кто клиент;
4. где это выполняется;
5. можно ли это сделать одному человеку;
6. это услуга, товар или смешанная модель;
7. есть ли риск перепродажи;
8. есть ли риск лицензии;
9. есть ли риск сотрудников;
10. есть ли риск, что это слишком широкое название.

Если смысл непонятен, статус:

`needs_data`

## 12. Источники профессии

Для кандидата нужно найти источник профессии или близкой деятельности.

Возможные источники:

1. классификатор;
2. профессиональный стандарт;
3. официальный документ;
4. внутренний проверенный список;
5. другой надёжный источник.

Правило:

1. профессия без источника не считается подтверждённой;
2. зеркало нужно помечать как зеркало;
3. совпадение только по слову не считается достаточным;
4. нужно проверять смысл;
5. если источника нет, статус `needs_source`.

## 13. Источники услуг

Для кандидата нужно определить услуги.

Направление без услуг не готово для бизнес-плана.

Нужно собрать:

1. список услуг;
2. описание каждой услуги;
3. тип клиента;
4. способ оказания услуги;
5. источник услуги;
6. город или регион, если важно.

Пример структуры:

```json
{
  "service_hypotheses": [
    {
      "service_key": "",
      "title_ru": "",
      "description": "",
      "customer_type": "individual | business | mixed | unknown",
      "delivery_mode": "home | client_location | rented_place | online | mixed | unknown",
      "source_evidence": [],
      "status": "candidate | confirmed | rejected | needs_source"
    }
  ]
}
```

## 14. Проверка НПД и ИП

Для кандидата нужно проверить налоговый и правовой режим.

Минимально проверить:

1. можно ли предварительно работать как самозанятый;
2. не нарушается ли лимит НПД;
3. нет ли риска работников;
4. нет ли риска перепродажи чужих товаров;
5. нет ли риска агентских или комиссионных схем;
6. не нужен ли ИП;
7. не нужны ли лицензии или разрешения;
8. нет ли риска маркированных товаров.

Структура:

```json
{
  "legal_tax_check": {
    "npd_possible_preliminary": null,
    "npd_limit_rub_per_year": 2400000,
    "ip_required_preliminary": null,
    "employees_risk": null,
    "resale_risk": null,
    "agency_scheme_risk": null,
    "marked_goods_risk": null,
    "license_or_permit_required": null,
    "status": "checked | insufficient_data | needs_source | blocked_legal",
    "source_evidence": [],
    "notes": ""
  }
}
```

Если правовая проверка не выполнена, кандидат не может попасть в пользовательский процесс.

## 15. Проверка соцконтракта

Если кандидат может использоваться для соцконтракта, нужен отдельный блок проверки.

Проверить:

1. подходит ли направление предварительно;
2. какие расходы могут быть допустимы;
3. какие расходы могут быть недопустимы;
4. нужна ли регистрация самозанятого или ИП;
5. нужны ли региональные правила;
6. нужна ли смета;
7. нужна ли отчётность;
8. не превышает ли стартовый бюджет лимит соцконтракта;
9. сколько своих денег может понадобиться сверх лимита.

Структура:

```json
{
  "social_contract_check": {
    "fit_preliminary": null,
    "max_support_rub": 350000,
    "training_support_rub": 30000,
    "startup_costs_within_limit": null,
    "own_money_required_rub": null,
    "regional_rules_required": true,
    "status": "checked | insufficient_data | needs_regional_rules | not_applicable",
    "source_evidence": [],
    "notes": ""
  }
}
```

Правило:

1. соцконтракт — отдельный режим;
2. нельзя считать, что все регионы одинаковые;
3. если регион неизвестен, статус должен быть неполным;
4. нельзя обещать одобрение соцконтракта.

## 16. Сбор цен услуг

Для кандидата нужно собрать цены услуг.

Правила:

1. цена должна иметь источник;
2. цена должна иметь дату;
3. цена должна иметь город или регион;
4. цена должна быть связана с конкретной услугой;
5. лучше хранить диапазон, а не одну цену;
6. цену нельзя придумывать;
7. устаревшая цена должна иметь статус.

Структура:

```json
{
  "service_price_facts": [
    {
      "service_key": "",
      "price_rub": null,
      "price_min_rub": null,
      "price_max_rub": null,
      "city": "",
      "region": "",
      "source_url": "",
      "source_type": "marketplace | manual_source | official | other",
      "collected_at": "",
      "valid_until": "",
      "confidence": "low | medium | high | unknown",
      "notes": ""
    }
  ]
}
```

## 17. Сбор цен оборудования

Для кандидата нужно собрать цены оборудования и инструментов.

Правила:

1. каждая позиция должна иметь источник;
2. цена должна иметь дату;
3. позиция должна иметь название;
4. позиция должна иметь количество;
5. позиция должна быть связана с вариантом запуска;
6. нужно разделять обязательные и желательные позиции;
7. нельзя считать старую цену актуальной бесконечно.

Структура:

```json
{
  "equipment_price_facts": [
    {
      "item": "",
      "category": "equipment | tools | materials | training | rent | advertising | registration | other",
      "amount_rub": null,
      "quantity": null,
      "required": true,
      "variant_key": "",
      "source_url": "",
      "collected_at": "",
      "valid_until": "",
      "confidence": "low | medium | high | unknown",
      "notes": ""
    }
  ]
}
```

## 18. Сбор стартовых расходов

Стартовые расходы должны считаться из строк.

Нельзя писать одну сумму без расшифровки.

Структура:

```json
{
  "startup_costs": [
    {
      "item": "",
      "category": "",
      "amount_rub": null,
      "required": true,
      "variant_key": "",
      "source_evidence": [],
      "last_checked_at": null,
      "notes": ""
    }
  ]
}
```

Если нет стартовых расходов, кандидат не готов для финансовой оценки.

## 19. Сбор текущих расходов

Текущие расходы должны храниться отдельно от стартовых.

Структура:

```json
{
  "monthly_fixed_costs": [
    {
      "item": "",
      "category": "",
      "amount_rub_per_month": null,
      "source_evidence": [],
      "last_checked_at": null,
      "notes": ""
    }
  ]
}
```

Если текущие расходы неизвестны, точка безубыточности будет неполной.

## 20. Сбор расходов на заказ

Расходы на заказ нужны для расчёта маржи и точки безубыточности.

Структура:

```json
{
  "variable_costs_per_order": [
    {
      "item": "",
      "category": "",
      "amount_rub_per_order": null,
      "source_evidence": [],
      "last_checked_at": null,
      "notes": ""
    }
  ]
}
```

Если расходов на заказ нет, расчёт может быть неполным.

## 21. Сбор рыночных сигналов

Рыночные сигналы нужны для понимания конкуренции и цен.

Примеры:

1. количество объявлений;
2. диапазон цен;
3. город;
4. дата;
5. тип услуги;
6. примеры предложений;
7. качество данных.

Правило:

1. количество объявлений не равно реальному спросу;
2. объявление не доказывает прибыль;
3. рыночный сигнал должен храниться как факт;
4. вывод должен храниться отдельно;
5. если источник недоступен, писать `недостаточно данных`.

## 22. Безопасность сбора

При сборе данных запрещено:

1. обходить капчу;
2. обходить логин;
3. использовать чужие учётные записи;
4. собирать контакты;
5. делать массовый сбор без ограничений;
6. использовать скрытый обход защиты;
7. нарушать правила площадки.

Если источник недоступен без таких действий, кандидат получает статус:

`needs_source`

или

`insufficient_data`

## 23. Авито

Авито может быть источником открытых рыночных сигналов только при безопасном доступе.

Разрешено:

1. точечная проверка открытой страницы;
2. сбор видимых названий;
3. сбор видимых цен;
4. сбор города;
5. сбор количества предложений, если видно;
6. сохранение даты;
7. сохранение запроса.

Запрещено:

1. логин;
2. обход капчи;
3. обход блокировки;
4. сбор контактов;
5. массовый сбор;
6. считать Авито единственным источником истины.

## 24. Ozon и закупочные площадки

Ozon и другие площадки могут быть источником цен оборудования, если доступ безопасен.

Разрешено:

1. открытые карточки товаров;
2. цена;
3. ссылка;
4. дата;
5. название товара;
6. количество;
7. вариант запуска.

Запрещено:

1. обход капчи;
2. обход блокировки;
3. логин без отдельного разрешения;
4. массовый сбор;
5. считать одну цену достаточной для уверенной сметы.

Если Ozon недоступен, нужно использовать другой источник или писать `недостаточно данных`.

## 25. Финансовая проверка кандидата

Кандидат должен пройти минимальную финансовую проверку.

Проверить:

1. есть ли стартовые расходы;
2. есть ли текущие расходы;
3. есть ли расходы на заказ;
4. есть ли цена услуги;
5. можно ли посчитать выручку;
6. можно ли посчитать точку безубыточности;
7. можно ли сравнить с бюджетом клиента;
8. можно ли сравнить с лимитом соцконтракта;
9. можно ли оценить риски;
10. каких данных не хватает.

Если данных не хватает, кандидат остаётся в статусе:

`needs_financial_inputs`

## 26. Точка безубыточности кандидата

Точка безубыточности считается только если есть данные.

Формула:

`точка безубыточности в заказах = постоянные расходы / (цена услуги - переменные расходы на заказ)`

Если нет цены услуги, постоянных расходов или переменных расходов, считать нельзя.

Если цена услуги меньше или равна переменным расходам на заказ, кандидат получает финансовый риск.

## 27. Бюджет клиента

Кандидат должен поддерживать будущую проверку бюджета клиента.

Пользователь сможет указать бюджет:

1. точной суммой: `1 200 000 рублей`;
2. верхней границей: `до 3 000 000 рублей`;
3. диапазоном: `от 500 000 до 1 500 000 рублей`;
4. неизвестным бюджетом.

Структура:

```json
{
  "budget_input_type": "exact | max | range | unknown",
  "budget_min_rub": null,
  "budget_max_rub": null,
  "budget_exact_rub": null,
  "budget_source": "user_input",
  "budget_purpose": "social_contract | own_money | grant | loan | mixed | unknown"
}
```

Сейчас подбор по бюджету не создаётся.

Сейчас фиксируется требование к будущей системе.

## 28. Проверка бюджета кандидата

Кандидат должен иметь предварительные поля стартового капитала.

Структура:

```json
{
  "candidate_capital_check": {
    "minimum_start_rub": null,
    "recommended_start_rub": null,
    "expanded_start_rub": null,
    "social_contract_fit_rub": 350000,
    "requires_more_than_social_contract": null,
    "budget_last_checked_at": null,
    "price_sources": [],
    "status": "calculated | insufficient_data | needs_price_update | needs_source"
  }
}
```

Если стартовый капитал неизвестен, кандидат нельзя использовать в пользовательском процессе.

## 29. Сценарии кандидата

Для кандидата можно готовить сценарии только при наличии данных.

Минимальные сценарии:

1. осторожный;
2. обычный;
3. сильный.

Сценарии не должны быть фантазиями.

Сценарии должны строиться из фактов.

Если фактов нет, сценарии не создаются.

## 30. Проверки качества кандидата

Кандидат должен иметь проверки качества.

Структура:

```json
{
  "candidate_quality_gates": {
    "has_profession_source": false,
    "has_service_list": false,
    "has_service_sources": false,
    "has_legal_tax_check": false,
    "has_social_contract_check": false,
    "has_startup_costs": false,
    "has_monthly_fixed_costs": false,
    "has_variable_costs": false,
    "has_service_prices": false,
    "has_market_facts": false,
    "has_break_even_inputs": false,
    "has_source_history": false,
    "ready_for_draft_base": false,
    "ready_for_working_base": false,
    "ready_for_user_flow": false
  }
}
```

Правило:

1. если `ready_for_user_flow` false, кандидат нельзя показывать как рекомендацию;
2. если `ready_for_working_base` false, кандидат нельзя использовать в рабочей базе;
3. если `ready_for_draft_base` true, кандидат можно перенести в черновую базу.

## 31. Уровень доверия кандидата

Кандидат должен иметь уровень доверия.

Минимальные уровни:

1. `low`;
2. `medium`;
3. `high`;
4. `unknown`.

Уровень доверия зависит от:

1. количества источников;
2. качества источников;
3. свежести цен;
4. полноты услуг;
5. полноты расходов;
6. юридической проверки;
7. проверки соцконтракта;
8. рыночных данных;
9. полноты финансовых входных данных.

Кандидат с низким доверием нельзя показывать пользователю как готовую рекомендацию.

## 32. Риски кандидата

Риски должны храниться структурно.

Структура:

```json
{
  "candidate_risks": [
    {
      "risk_type": "legal | tax | market | budget | skill | seasonality | location | data_quality | source_quality | other",
      "level": "low | medium | high | unknown",
      "description": "",
      "based_on_facts": [],
      "mitigation": "",
      "notes": ""
    }
  ]
}
```

Риск не должен быть голословным.

Если риск основан на фактах, нужно указать факты.

Если риск основан на слабом источнике, нужно снизить доверие.

## 33. Причины отложения кандидата

Кандидат может быть отложен.

Причины:

1. мало источников;
2. нет цен услуг;
3. нет цен оборудования;
4. нет текущих расходов;
5. нет расходов на заказ;
6. неясен налоговый режим;
7. неясен соцконтракт;
8. неясны услуги;
9. непонятен клиент;
10. рынок недоступен;
11. источники заблокированы;
12. данные противоречат друг другу;
13. цены устарели.

Структура:

```json
{
  "postponement": {
    "reason": "",
    "missing_data": [],
    "next_collection_steps": [],
    "created_at": "",
    "notes": ""
  }
}
```

## 34. Причины отклонения кандидата

Кандидат может быть отклонён.

Причины:

1. запрещённая деятельность;
2. высокий юридический риск;
3. нет понятной услуги;
4. направление не подходит для одного человека;
5. нужно много сотрудников;
6. нужна лицензия, которую невозможно учесть в текущем продукте;
7. направление основано на перепродаже, если это конфликтует с режимом НПД;
8. источники не подтверждают смысл;
9. направление является дублем;
10. данные слишком слабые.

Структура:

```json
{
  "rejection": {
    "reason": "",
    "based_on_facts": [],
    "rejected_at": "",
    "notes": ""
  }
}
```

## 35. Принятие кандидата в черновую базу

Кандидат может быть принят в черновую базу, если:

1. понятна профессия;
2. понятна специальность или услуга;
3. есть хотя бы один источник профессии или услуги;
4. есть список услуг;
5. есть предварительная правовая проверка;
6. есть предварительные данные по расходам или явно указано, чего не хватает;
7. есть статус;
8. есть история источников;
9. есть список недостающих данных.

Черновая база не равна пользовательской базе.

Кандидат в черновой базе нельзя показывать пользователю как готовую рекомендацию.

## 36. Принятие кандидата в рабочую базу

Кандидат может быть принят в рабочую базу, если:

1. есть источники профессии;
2. есть подтверждённые услуги;
3. есть цены услуг;
4. есть стартовые расходы;
5. есть текущие расходы;
6. есть расходы на заказ или явная причина их отсутствия;
7. есть налоговая проверка;
8. есть проверка соцконтракта, если нужен режим соцконтракта;
9. есть источники цен оборудования;
10. есть история источников;
11. есть уровень доверия;
12. есть проверки качества;
13. есть статус.

Рабочая база ещё не обязательно означает пользовательскую рекомендацию.

## 37. Допуск к пользовательскому процессу

Направление можно использовать в пользовательском процессе только если:

1. статус `ready_for_user_flow`;
2. есть источники;
3. есть услуги;
4. есть цены;
5. есть расходы;
6. есть финансовые входные данные;
7. есть правовая проверка;
8. есть проверка соцконтракта, если режим соцконтракт;
9. есть дата обновления цен;
10. есть история источников;
11. есть проверка, что данные не устарели;
12. нет блокирующих рисков.

Если хотя бы один критический блок отсутствует, направление нельзя использовать как готовую рекомендацию.

## 38. Мониторинг новых специальностей

В будущем система может мониторить появление новых специальностей.

Но мониторинг не должен автоматически добавлять специальность в рабочую базу.

Мониторинг может только:

1. создать кандидата;
2. сохранить источник;
3. сохранить причину обнаружения;
4. поставить статус `new`;
5. поставить задачу на сбор данных.

Мониторинг не должен:

1. делать пользовательскую рекомендацию;
2. считать бизнес-план;
3. обещать прибыль;
4. обходить ограничения сайтов;
5. собирать контакты;
6. добавлять направление без проверки.

## 39. Автоматизация без обязательного человека

Клиентский процесс должен быть автоматизирован.

Человек не должен быть обязательной частью клиентского процесса.

Внутренняя ручная проверка может использоваться только для:

1. улучшения базы;
2. настройки правил;
3. проверки спорных источников;
4. анализа ошибок;
5. подготовки новых документов.

Но пользовательский результат не должен требовать ручной работы человека как обязательного шага.

## 40. Заменяемые инструменты

Добавление новых специальностей не должно зависеть от одного инструмента.

Роли:

1. сборщик информации;
2. аналитик;
3. проверяющий;
4. составитель базы;
5. собеседник с клиентом.

Каждая роль должна быть заменяемой.

Роль может работать:

1. через командную строку;
2. через API.

Пример:

1. сегодня сборщик может быть Codex + браузер;
2. завтра сборщик может быть MiMo + браузер;
3. аналитик может быть MiMo;
4. аналитик может быть DeepSeek;
5. любая роль может быть заменена, если вход и выход структурные.

Пример:
