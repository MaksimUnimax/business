# Проверки готовности

## 1. Назначение документа

Этот документ описывает проверки готовности проекта.

Документ нужен для разработки.

Этот документ не является кодом.

Этот документ не запускает тесты.

Этот документ не меняет базу.

Этот документ не создаёт бизнес-план.

Этот документ фиксирует, как понять, что документы, база, источники, финансовая аналитика, бизнес-план, роли ИИ и будущая автоматизация готовы к следующему этапу.

## 2. Главный принцип

Нельзя считать этап готовым только потому, что файл создан.

Этап готов только если:

1. нужные документы есть;
2. смысловые требования внутри документов есть;
3. нет противоречий;
4. нет выдуманных данных;
5. есть правила остановки;
6. есть источники или пометка, что источник нужен;
7. понятны недостающие данные;
8. понятны запреты;
9. результат сохранён в Git;
10. можно восстановить контекст после обрыва чата.

## 3. Что проверки не должны делать

Проверки не должны:

1. менять базу;
2. создавать новые направления;
3. запускать подбор;
4. запускать вопросы;
5. запускать рекомендации;
6. запускать рынок;
7. запускать Авито;
8. запускать Ozon;
9. запускать внешние ИИ;
10. менять API;
11. менять CLI;
12. делать бизнес-план для клиента;
13. подставлять недостающие данные;
14. считать документ готовым без содержательной проверки.

## 5. Проверка Git

Перед любой задачей нужно проверить:

1. рабочая папка правильная;
2. repo чистый;
3. нет неожиданных файлов;
4. понятен текущий commit;
5. понятен текущий branch;
6. есть backup tag перед изменениями;
7. после изменения есть commit;
8. после commit есть push;
9. после push repo снова чистый.

Минимальные команды:

```bash
pwd
git status --short --untracked-files=all
git log --oneline -8
```

Если repo не чистый, работа должна остановиться.

Стоп:

`STOP_REPO_NOT_CLEAN`

## 6. Проверка backup

Перед изменениями должен быть backup.

Для документов достаточно backup tag.

Для кода и данных может потребоваться:

1. backup tag;
2. backup branch;
3. копия файлов;
4. backup базы или состояния, если меняется база.

Правило:

Если изменение может повлиять на код, данные, миграции или runtime, backup должен быть отдельным явным шагом.

## 7. Проверка изменённых файлов

После задачи нужно проверить, что изменились только ожидаемые файлы.

Если задача была про документ, не должны измениться:

1. код;
2. база;
3. тесты;
4. скрипты;
5. настройки;
6. секреты;
7. файлы окружения.

Если изменились лишние файлы, работа должна остановиться.

Стоп:

`ERROR_UNEXPECTED_FILES_CHANGED`

## 8. Проверка commit и push

После успешной задачи нужно проверить:

1. есть commit hash;
2. commit message соответствует задаче;
3. push выполнен;
4. git status чистый;
5. GitHub показывает commit;
6. нужный файл виден в GitHub.

Если commit или push отсутствует, задача не считается завершённой.

3. есть ли дата;
4. понятен ли тип источника;

## 22. Проверка цен

Для цен нужно проверять:

1. есть ли источник;
2. есть ли дата;
3. есть ли город или регион;
4. понятно ли, что это за товар или услуга;
5. цена не пустая;
6. цена не выглядит явно ошибочной;
7. есть ли статус актуальности;
8. цена не устарела;
9. есть ли несколько источников, если нужен уверенный вывод;
10. есть ли диапазон цен, если цена сильно меняется.

Если цена устарела, нужен статус:

`needs_price_update`

## 23. Проверка финансовых расчётов

## 24. Проверка точки безубыточности

Точка безубыточности может считаться только если есть:

1. цена услуги;
2. постоянные расходы;
3. переменные расходы на заказ.

Формула:

`точка безубыточности в заказах = постоянные расходы / (цена услуги - переменные расходы на заказ)`

Если данных нет, писать:

`недостаточно данных`

Если цена услуги меньше или равна переменным расходам, модель не выходит в ноль.

## 25. Проверка бюджета клиента

Система должна поддерживать бюджет:

1. точной суммой: `1 200 000 рублей`;
2. верхней границей: `до 3 000 000 рублей`;
3. диапазоном: `от 500 000 до 1 500 000 рублей`;
4. неизвестным бюджетом.

Структура должна содержать:

```json
{
  "budget_input_type": "exact | max | range | unknown",
  "budget_min_rub": null,
  "budget_max_rub": null,
  "budget_exact_rub": null
}
```

Если бюджет неизвестен, система не должна делать вывод, что бюджета хватает.

## 26. Проверка соцконтракта

Для режима соцконтракта нужно проверять:

1. лимит суммы;
2. обучение;
3. допустимые расходы;
4. недопустимые расходы;
5. региональные правила;
6. отчётность;
7. срок договора;
8. регистрацию самозанятого или ИП;
9. собственные деньги сверх лимита;
10. предупреждение, что одобрение не гарантируется.

Если региональные правила неизвестны, статус должен быть:

`needs_regional_rules`

## 27. Проверка НПД

Для НПД нужно проверять:

1. лимит 2,4 млн рублей в год;
2. работников;
3. перепродажу;
4. агентские схемы;
5. комиссионные схемы;
6. маркированные товары;
7. источник правила;
8. дату источника.

Если НПД не подходит, нужно объяснить причину.

## 28. Проверка пользовательского результата

Пользовательский результат нельзя выдавать, если:

1. направление черновое;
2. направление не имеет статус `ready_for_user_flow`;
3. нет источников;
4. нет цен;
5. нет расходов;
6. нет налоговой проверки;
7. нет проверки соцконтракта для режима соцконтракта;
8. цены устарели;
9. есть юридический блок;
10. не хватает данных для ключевых расчётов.

Если данных не хватает, нужно объяснить это простым языком.

## 29. Запрещённые формулировки

Запрещено писать:

1. `гарантированная прибыль`;
2. `точно одобрят`;
3. `бизнес обязательно окупится`;
4. `рисков нет`;
5. `спрос высокий`, если нет источника;
6. `конкуренции нет`, если нет источника;
7. `цены актуальны`, если нет даты;
8. `можно запускать`, если расчёты неполные;
9. `подходит`, если нет проверки бюджета;
10. `одобрят соцконтракт`, в любой форме.

## 30. Проверка безопасности сбора

Запрещено без отдельного решения:

1. обход капчи;
2. обход логина;
3. использование чужих учётных записей;
4. скрытые прокси;
5. сбор контактов;
6. массовый сбор без ограничений;
7. нарушение правил площадки;
8. использование платных сомнительных сервисов.

Если источник недоступен, нужно писать:

`недостаточно данных`

или искать другой разрешённый источник.

## 31. Проверка Авито

Авито можно использовать только как безопасный источник открытых рыночных сигналов.

Проверки:

1. нет логина;
2. нет обхода капчи;
3. нет обхода блокировки;
4. нет сбора контактов;
5. нет массового сбора;
6. есть дата проверки;
7. есть город;
8. есть запрос;
9. есть видимые факты;
10. есть статус, если источник заблокирован.

Авито не доказывает прибыль.

## 32. Проверка Ozon и закупочных источников

Ozon и другие закупочные источники можно использовать только при безопасном доступе.

Проверки:

1. есть открытая цена;
2. есть ссылка;
3. есть дата;
4. есть название товара;
5. есть количество;
6. есть вариант запуска;
7. нет обхода капчи;
8. нет обхода блокировки;
9. нет логина без разрешения;
10. нет массового сбора.

Одна цена не должна считаться достаточной для уверенной сметы.

## 33. Проверка ролей ИИ

Для каждой роли нужно проверить:

1. есть ли вход;
2. есть ли выход;
3. есть ли разрешённые действия;
4. есть ли запрещённые действия;
5. есть ли формат ошибки;
6. есть ли история выполнения;
7. есть ли способ запуска;
8. есть ли возможность замены;
9. не теряются ли источники;
10. не смешиваются ли факты и выводы.

## 34. Проверка замены ИИ

ИИ или инструмент можно заменить только если:

1. новый инструмент понимает вход роли;
2. новый инструмент возвращает нужный выход;
3. новый инструмент сохраняет источники;
4. новый инструмент сохраняет ошибки;
5. новый инструмент соблюдает запреты;
6. новый инструмент не ломает базу;
7. новый инструмент не ломает историю;
8. новый инструмент не требует ручного человека в клиентском процессе.

Если этого нет, заменять нельзя.

## 35. Проверка бизнес-плана

Бизнес-план считается готовым только если:

1. имеет статус;
2. имеет режим;
3. имеет бюджет клиента;
4. имеет направление;
5. имеет услуги;
6. имеет источники;
7. имеет смету;
8. имеет стартовые расходы;
9. имеет текущие расходы;
10. имеет расходы на заказ или причину отсутствия;
11. имеет финансовые расчёты или причину невозможности;
12. имеет риски;
13. имеет недостающие данные;
14. имеет предупреждения;
15. не обещает прибыль;
16. не обещает соцконтракт.

## 37. Проверка готовности к мосту ChatGPT-MiMo/Codex

После завершения документов можно переходить к проектированию моста.

Но перед этим нужно проверить:

1. документы сохранены в Git;
2. repo чистый;
3. понятен следующий этап;
4. есть правила ролей ИИ;
5. есть правила безопасности;

10. есть Git как источник правды.

## 38. Проверки будущего моста

Будущий мост должен проверяться отдельно.

Минимальные проверки:

1. расширение не придумывает prompt;
2. расширение только переносит сообщения;
3. сервер не выполняет произвольную команду от расширения;
4. сервер принимает только задачу;
5. runner запускает только разрешённого исполнителя;
6. MiMo или Codex пишет отчёт;
7. отчёт возвращается в чат;
8. ChatGPT даёт следующий prompt;
9. цикл останавливается при STOP;
10. цикл останавливается при грязном repo;
11. цикл останавливается при лишних изменениях;
12. цикл останавливается при ошибке исполнителя;
13. цикл останавливается при запросе секретов;
14. цикл останавливается при необходимости денег, логина или деплоя.

## 39. Стоп-условия

Система должна останавливаться, если:

1. repo не чистый;
2. изменены лишние файлы;
3. нет backup;
4. нет отчёта;
5. отчёт противоречит Git;
6. commit отсутствует;
7. push отсутствует;
8. нужны секреты;
9. нужен логин;
10. нужен платный сервис;
11. нужна миграция базы;
12. нужен deploy;
13. нужен обход капчи;
14. нужен массовый сбор;
15. нужен выбор пользователя;
16. возникло непонятное решение;
17. достигнут лимит шагов;
18. появился файл `STOP_AUTOMATION`.

## 40. Проверка отчёта исполнителя

Отчёт исполнителя должен содержать:

1. режим работы;

10. проверки содержания;
11. проверки безопасности;
12. решение;
13. следующий шаг.

Если отчёт неполный, результат нужно перепроверять.

## 41. Проверка GitHub

После push нужно проверять GitHub.

Проверить:

1. commit есть;
2. файл есть;
3. путь правильный;
4. содержание соответствует задаче;
5. лишние файлы не добавлены;
6. commit message соответствует задаче.

Нельзя полагаться только на отчёт исполнителя.

## 42. Проверка обрыва диалога

После каждого важного этапа нужно обновлять контекст.

Минимально контекст должен позволять восстановить:

1. текущий этап;
2. последний commit;
3. что уже сделано;
4. что не сделано;
5. какие решения приняты;
6. какие файлы важны;
7. следующий шаг;
8. запреты;
9. стоп-условия.

## 43. Проверка перехода к разработке

К разработке можно переходить только если:

1. весь комплект документов есть;
2. документы закоммичены;
3. документы запушены;
4. GitHub проверен;
5. repo чистый;
6. нет незавершённых документальных задач;
7. понятен первый технический этап;
8. есть backup-правила;
9. есть правила остановки;
10. пользователь подтвердил переход к разработке.

## 44. Проверка перехода к мосту

К мосту можно переходить только после документации.

Первый этап моста должен быть не боевым автопилотом, а безопасным прототипом.

Минимальный прототип:

1. расширение или переносчик сообщений;
2. серверный мост;
3. очередь задач;
4. runner;
5. запуск MiMo как исполнителя;
6. отчёт в outbox;
7. возврат отчёта в чат;
8. остановка по STOP;
9. запрет произвольных shell-команд;
10. журнал цикла.

## 45. Что не считается готовностью

Не считается готовностью:

1. файл создан, но не закоммичен;
2. commit есть, но push нет;
3. отчёт есть, но GitHub не проверен;
4. документ есть, но нет ключевых требований;
5. расчёт есть, но нет источников;
6. цена есть, но нет даты;
7. бизнес-план есть, но обещает прибыль;
8. направление есть, но статус черновой;
9. кандидат есть, но используется как рекомендация;
10. ИИ сделал вывод, но нет фактов.
