# Основание для ТЗ: база направлений и финансовая аналитика

## 1. Что строим

Мы строим систему для подготовки бизнес-планов на основе проверяемой базы профессий, специальностей, услуг и направлений.

Система не должна придумывать направления из головы. Направление должно попадать в базу только через источники, проверку и расчёты.

Соцконтракт — это один из режимов работы системы, но не единственный. Система должна уметь готовить бизнес-план:

1. под соцконтракт;
2. под запуск на свои деньги;
3. под запуск с бюджетом больше 350 000 рублей;
4. под другой вид поддержки, если позже он будет добавлен;
5. под обычный бизнес-план без соцконтракта.

Бюджет не должен быть одним жёстким числом. Пользователь в будущем должен иметь возможность указать бюджет:

1. точной суммой: например, `1 200 000 рублей`;
2. верхней границей: например, `до 3 000 000 рублей`;
3. диапазоном: например, `от 500 000 до 1 500 000 рублей`;
4. неизвестным бюджетом: тогда система должна показать, какие данные нужны для расчёта.

Бюджет должен использоваться для выбора подходящих направлений-кандидатов и для составления бизнес-плана. Но сейчас этот подбор не делаем. Сейчас только фиксируем требование в ТЗ.

## 2. Что не делаем сейчас

Сейчас не делаем:

1. подбор человеку;
2. вопросы теста;
3. рекомендации;
4. конкретные бизнес-планы;
5. расчёт конкретной прибыли;
6. проверку рынка через Авито, Ozon или другие площадки;
7. закупки;
8. рекламу;
9. финальную базу;
10. пользовательский продукт.

Сейчас задача — подготовить основу для ТЗ и определить, как должна быть устроена база.

## 3. Главное правило проекта

В области финансовой аналитики и бизнес-планов нельзя сочинять.

Все правила расчётов, структура бизнес-плана, финансовые показатели, способы оценки и требования к данным должны браться из проверенных источников:

1. официальные источники;
2. профильные организации по малому бизнесу;
3. шаблоны бизнес-планов;
4. шаблоны финансовых прогнозов;
5. методики расчёта расходов, точки безубыточности и движения денег;
6. российские правила соцконтракта;
7. российские правила самозанятости и ИП;
8. источники цен оборудования и услуг.

Если нет источника, то в документе нужно писать:

`нужно подтвердить источником`

## 4. Проверенные источники и что из них берём

| Источник | Что подтверждает | Как используем |
| --- | --- | --- |
| SBA: Write your business plan | Бизнес-план нужен как основа бизнеса, для запуска, управления и привлечения денег | Берём структуру: описание бизнеса, рынок, продажи, финансы |
| SBA: Break-even point | Точка безубыточности считается через постоянные расходы, цену и переменные расходы | В базе направления нужны цена услуги, постоянные расходы, переменные расходы |
| SBA: Startup costs | Перед запуском нужно считать стартовые расходы, деньги для запуска и точку безубыточности | В базе нужны стартовые траты и запас денег |
| SCORE: Financial projections template | Нужны стартовые расходы, прогноз продаж, текущие расходы, движение денег, прибыль/убыток, баланс, точка безубыточности, показатели | Используем как основу финансовой части бизнес-плана |
| LivePlan и похожие сервисы | Такие сервисы строят план через ввод исходных данных, расчёты, проверку идеи, рынок и финансовый прогноз | Наша система тоже должна отделять входные данные, расчёты и выводы |
| Правила соцконтракта | Для соцконтракта есть лимит до 350 000 рублей на дело, обучение до 30 000 рублей, целевые траты, отчётность и региональные правила | Соцконтракт — отдельный режим, не просто обычный бизнес-план с другим бюджетом |
| ФНС / НПД | У самозанятых есть лимит 2,4 млн рублей в год, ограничения по перепродаже, работникам и агентским схемам | В базе у каждого направления нужны налоговые ограничения |

## 5. Соцконтракт и обычный бизнес-план

Соцконтракт отличается от обычного бизнес-плана не только суммой 350 000 рублей.

Для соцконтракта нужно учитывать:

1. лимит суммы;
2. целевое расходование денег;
3. допустимые и недопустимые траты;
4. региональные правила;
5. отчётность;
6. срок действия договора;
7. требование показать, как дело даст доход;
8. возможные ограничения по аренде;
9. регистрацию самозанятого или ИП;
10. требования соцзащиты.

Обычный бизнес-план может иметь больший бюджет. Например:

1. 500 000 рублей;
2. 1 200 000 рублей;
3. до 3 000 000 рублей;
4. любой другой бюджет, который указал клиент.

Для обычного бизнес-плана меняются:

1. список оборудования;
2. стартовые траты;
3. срок запуска;
4. срок окупаемости;
5. риски;
6. требования к помещению;
7. требования к рекламе;
8. расчёт денег;
9. формат вывода.

## 6. Как хранить бюджет в базе

Нельзя хранить бюджет как одно поле "до 350 000 рублей".

Бюджет направления должен считаться из строк расходов.

Для каждого направления нужно хранить:

1. минимальный запуск;
2. нормальный запуск;
3. расширенный запуск;
4. запуск под соцконтракт;
5. запуск на свои деньги;
6. запуск с большим бюджетом;
7. запуск с неизвестным бюджетом, когда система должна запросить недостающие данные.

Для будущей системы нужно заложить ввод бюджета пользователем:

```json
{
  "budget_input_type": "exact | max | range | unknown",
  "budget_min_rub": null,
  "budget_max_rub": null,
  "budget_exact_rub": null,
  "budget_source": "user_input",
  "budget_purpose": "social_contract | own_money | grant | loan | mixed | unknown"
}
```

Примеры:

```json
{
  "budget_input_type": "exact",
  "budget_exact_rub": 1200000,
  "budget_min_rub": 1200000,
  "budget_max_rub": 1200000
}
```

```json
{
  "budget_input_type": "max",
  "budget_exact_rub": null,
  "budget_min_rub": 0,
  "budget_max_rub": 3000000
}
```

```json
{
  "budget_input_type": "range",
  "budget_exact_rub": null,
  "budget_min_rub": 500000,
  "budget_max_rub": 1500000
}
```

Для каждого направления нужно хранить:

```json
{
  "capital_requirements": {
    "minimum_start_rub": null,
    "recommended_start_rub": null,
    "expanded_start_rub": null,
    "social_contract_fit_rub": 350000,
    "requires_more_than_social_contract": null,
    "budget_last_checked_at": null,
    "price_sources": []
  }
}
```

Система в будущем должна уметь сравнивать бюджет клиента с направлением:

```json
{
  "budget_fit": {
    "fits_minimum_start": true,
    "fits_recommended_start": false,
    "fits_expanded_start": false,
    "missing_budget_amount_rub": null,
    "budget_risk": "low | medium | high",
    "explanation": ""
  }
}
```

Сейчас этот подбор не делаем. Сейчас только фиксируем требование.

## 7. Что должна хранить база направления

Каждая запись направления должна хранить:

1. ключ направления;
2. русское название;
3. профессия;
4. специальность;
5. список услуг;
6. вариант запуска;
7. форма работы: самозанятый, ИП, требует проверки;
8. можно ли предварительно применять НПД;
9. ограничения НПД;
10. нужен ли ИП;
11. нужны ли лицензии или разрешения;
12. стартовые траты;
13. текущие траты в месяц;
14. траты на один заказ;
15. цены услуг;
16. конкуренты;
17. спрос;
18. точка безубыточности;
19. окупаемость;
20. денежный запас;
21. риски;
22. источники;
23. дата обновления цен;
24. дата следующей проверки;
25. статус доверия;
26. статус направления: черновик, требует данных, можно использовать, нельзя использовать.

## 8. Минимум данных для оценки направления

Для нормальной оценки направления нужны минимум такие данные:

1. что продаём;
2. кому продаём;
3. город или регион;
4. цена услуги;
5. количество конкурентов;
6. диапазон цен конкурентов;
7. стартовые покупки;
8. цена оборудования;
9. текущие расходы;
10. расходы на один заказ;
11. сколько заказов нужно для выхода в ноль;
12. сколько денег нужно до первых продаж;
13. какие ограничения по налогам;
14. какие ограничения по соцконтракту;
15. какие риски;
16. какие источники подтверждают каждую цифру.

Если этих данных нет, направление не должно попадать в рабочую базу. Оно должно попадать в отложенные или в кандидаты на сбор данных.

## 9. Безопасная база и полная база

Полная база — это когда мы пытаемся собрать всё подряд из справочников.

Проблема полной базы:

1. будет много дублей;
2. будут слишком широкие названия;
3. будут устаревшие профессии;
4. будут профессии без понятной услуги;
5. будут направления без рынка;
6. будут направления без бюджета;
7. будут направления с юридическими ограничениями;
8. будут совпадения только по словам, но не по смыслу;
9. будут направления, где нельзя нормально сделать бизнес-план.

Безопасная база — это меньше направлений, но каждое направление имеет минимальные доказательства:

1. есть источники;
2. понятно, что продаём;
3. понятно, кому продаём;
4. понятен бюджет запуска;
5. понятны расходы;
6. понятна цена услуги;
7. понятны ограничения;
8. можно посчитать хотя бы грубую точку безубыточности;
9. есть дата обновления данных.

Для первого рабочего варианта нужна безопасная база. Полную базу можно собирать отдельно как большой сырой список, но не использовать её напрямую для бизнес-плана.

## 10. Пример отложенного направления

Пример: фотография и видео.

Нельзя просто написать "фотограф" и добавить в базу.

Нужно понять:

1. что именно продаёт человек;
2. фото на документы или семейные съёмки;
3. предметная съёмка или свадьбы;
4. нужен ли фотоаппарат;
5. нужен ли свет;
6. нужен ли ноутбук;
7. нужны ли программы;
8. нужна ли студия;
9. какие цены в городе;
10. сколько конкурентов;
11. какие расходы;
12. можно ли начать с малым бюджетом;
13. подходит ли это под соцконтракт;
14. какие риски.

Пока этих данных нет, направление должно быть отложено.

## 11. Как добавлять новые специальности

Новая специальность не должна сразу попадать в рабочую базу.

Путь добавления:

1. найден кандидат;
2. создана карточка кандидата;
3. собраны источники по профессии;
4. собраны источники по услугам;
5. собраны цены услуг;
6. собраны цены оборудования;
7. собраны текущие расходы;
8. проверены налоги;
9. проверены ограничения НПД;
10. проверены ограничения ИП;
11. проверены ограничения соцконтракта;
12. посчитаны стартовые траты;
13. посчитана точка безубыточности;
14. сделаны сценарии;
15. поставлен статус.

Возможные статусы:

1. можно добавить в базу;
2. мало данных;
3. рискованно;
4. нельзя использовать;
5. нужно обновить цены;
6. нужно проверить вручную источники;
7. нужно проверить юридические ограничения.

## 12. Как отделять факты от выводов

Факт и вывод должны храниться отдельно.

Пример факта:

```json
{
  "fact_type": "service_price",
  "value": 2500,
  "currency": "RUB",
  "city": "Новосибирск",
  "source_url": "",
  "collected_at": "",
  "collector": ""
}
```

Пример вывода:

```json
{
  "conclusion_type": "price_level",
  "value": "средний уровень цены",
  "based_on_facts": [],
  "reason": "цена попадает в середину найденного диапазона",
  "analyst": "",
  "created_at": ""
}
```

Требование:
если заменить аналитика, факты должны остаться, а вывод можно пересчитать.

## 13. Заменяемые исполнители

Систему нельзя жёстко привязывать к Codex, MiMo, DeepSeek или любому другому названию.

Должны быть роли:

1. сборщик информации;
2. аналитик;
3. составитель бизнес-плана;
4. проверяющий;
5. собеседник с клиентом.

Каждую роль можно заменить.

Каждая роль должна иметь общий вход и выход.

Каждая роль может работать:

1. через командную строку;
2. через API.

Сейчас возможная схема:

1. Codex + браузер собирает информацию по ссылкам;
2. MiMo делает анализ;
3. другая модель может общаться с клиентом.

Но это не должно быть жёстким правилом.

Завтра можно заменить:

1. Codex на MiMo с браузером;
2. MiMo на DeepSeek;
3. DeepSeek на другую модель;
4. API-модель на CLI-модель;
5. CLI-модель на API-модель.

## 14. Сборщик информации

Сборщик информации не обязан анализировать.

Текущий принцип:

1. сборщик ходит по заданным ссылкам;
2. собирает факты;
3. сохраняет цену, город, дату, источник;
4. не делает финансовые выводы;
5. не придумывает, подходит направление или нет.

Это нужно для экономии и контроля качества.

Если позже появится другой инструмент, его можно поставить на место сборщика.

## 15. Аналитик

Аналитик берёт собранные факты и делает выводы:

1. хватает ли бюджета;
2. сколько нужно заказов;
3. какие расходы критичны;
4. где риск;
5. где не хватает данных;
6. можно ли считать направление пригодным для базы.

Аналитик должен быть заменяемым.

Если анализ MiMo плохой, можно заменить его на DeepSeek или другую модель.

Если анализ через API лучше, можно использовать API.

Если анализ через командную строку дешевле, можно использовать командную строку.

## 16. Составитель бизнес-плана

Составитель бизнес-плана не должен придумывать цифры.

Он должен брать:

1. направление из базы;
2. бюджет клиента;
3. собранные цены;
4. расходы;
5. ограничения;
6. режим плана: соцконтракт или обычный план;
7. шаблон плана;
8. расчёты;
9. источники.

Если данных не хватает, он должен писать:

`недостаточно данных`

а не придумывать.

## 17. История источников

Обязательно хранить историю источников.

Для каждой цифры и каждого вывода нужно хранить:

1. источник;
2. ссылку;
3. дату;
4. город;
5. что именно извлекли;
6. кто извлёк;
7. какой инструмент использовался;
8. какая модель использовалась;
9. какой был запрос;
10. какая версия расчёта;
11. когда нужно обновить.

## 18. Обновление цен

Цены оборудования и услуг меняются.

Поэтому каждая цена должна иметь:

1. дату сбора;
2. источник;
3. город;
4. срок действия;
5. дату следующего обновления;
6. статус: свежая, устарела, требует проверки.

База не должна считать старые цены актуальными бесконечно.

## 19. Сценарии расчёта

Для каждого направления нужно хранить несколько сценариев.

Минимальный набор:

1. осторожный сценарий;
2. обычный сценарий;
3. сильный сценарий.

Сценарии должны отличаться не фантазиями, а входными данными:

1. цена услуги;
2. количество заказов;
3. расходы;
4. реклама;
5. загрузка;
6. стартовый бюджет.

Каждый сценарий должен хранить источники и дату.
