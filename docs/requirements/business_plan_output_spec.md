# Формат бизнес-плана

## 1. Назначение документа

Этот документ описывает, из каких блоков будущая система должна собирать бизнес-план.

Документ нужен для разработки.

Этот документ не является кодом.

Этот документ не создаёт бизнес-план для конкретного человека.

Этот документ не запускает расчёты.

Этот документ не запускает подбор.

Этот документ фиксирует структуру результата, чтобы система не писала бизнес-план свободной фантазией.

## 2. Главный принцип

Бизнес-план должен собираться из проверяемых блоков.

Каждый блок должен брать данные из:

1. базы направлений;
2. фактов;
3. источников;
4. расчётов;
5. бюджета клиента;
6. режима бизнес-плана;
7. правил финансовой аналитики;
8. правил источников;
9. правил соцконтракта, если режим соцконтракт.

Если данных не хватает, система должна писать:

`недостаточно данных`

Если методика не подтверждена источником, система должна писать:

`нужно подтвердить источником`

Бизнес-план не должен скрывать отсутствие данных.

## 3. Что бизнес-план не должен делать

Бизнес-план не должен:

1. обещать прибыль;
2. обещать одобрение соцконтракта;
3. обещать успех бизнеса;
4. придумывать цены;
5. придумывать расходы;
6. придумывать спрос;
7. придумывать конкурентов;
8. придумывать источники;
9. использовать устаревшие цены как свежие;
10. смешивать факт и вывод;
11. выдавать черновое направление как финальную рекомендацию;
12. подставлять недостающие цифры из головы;
13. скрывать риски;
14. скрывать, что данных не хватает;
15. писать "выгодно" без расчёта.

## 4. Режимы бизнес-плана

Система должна поддерживать несколько режимов.

Минимальные режимы:

1. бизнес-план под соцконтракт;
2. обычный бизнес-план;
3. бизнес-план под запуск на свои деньги;
4. бизнес-план под бюджет больше 350 000 рублей;
5. бизнес-план с неизвестным бюджетом;
6. бизнес-план под другой источник денег, если он будет добавлен позже.

Соцконтракт — один режим, но не вся система.

## 5. Бизнес-план под соцконтракт

Бизнес-план под соцконтракт должен учитывать:

1. лимит суммы;
2. целевое расходование денег;
3. допустимые расходы;
4. недопустимые расходы;
5. обучение;
6. региональные правила;
7. отчётность;
8. срок действия договора;
9. регистрацию самозанятого или ИП;
10. требование показать, как дело даст доход;
11. смету;
12. риск, что региональные правила не найдены.

Система не должна обещать, что соцконтракт одобрят.

Если региональные правила не найдены, бизнес-план должен иметь статус неполных данных.

## 6. Обычный бизнес-план

Обычный бизнес-план не должен автоматически наследовать ограничения соцконтракта.

Обычный бизнес-план должен учитывать:

1. бюджет пользователя;
2. стартовые расходы;
3. текущие расходы;
4. расходы на один заказ;
5. цены услуг;
6. рынок;
7. конкурентов;
8. налоговый режим;
9. точку безубыточности;
10. окупаемость;
11. движение денег;
12. риски;
13. источники;
14. недостающие данные.

## 7. Бюджет клиента

Бизнес-план должен принимать бюджет клиента в нескольких формах.

Пользователь может указать бюджет:

1. точной суммой: `1 200 000 рублей`;
2. верхней границей: `до 3 000 000 рублей`;
3. диапазоном: `от 500 000 до 1 500 000 рублей`;
4. неизвестным бюджетом.

Структура бюджета:

```json
{
  "budget_input_type": "exact | max | range | unknown",
  "budget_min_rub": null,
  "budget_max_rub": null,
  "budget_exact_rub": null,
  "budget_source": "user_input",
  "budget_purpose": "social_contract | own_money | grant | loan | mixed | unknown"
}
```

Правила:

1. если бюджет точной суммой, расчёт сравнивается с этой суммой;
2. если бюджет "до суммы", расчёт сравнивается с верхней границей;
3. если бюджет диапазоном, расчёт должен учитывать минимум и максимум;
4. если бюджет неизвестен, система должна показать, какие данные нужны;
5. если бюджет не хватает, система должна показать недостающую сумму;
6. нельзя считать направление подходящим, если стартовые расходы неизвестны.

## 8. Общая структура бизнес-плана

Бизнес-план должен состоять из блоков.

Минимальные блоки:

1. титульные данные;
2. краткое описание;
3. направление и услуги;
4. данные пользователя;
5. бюджет клиента;
6. режим бизнес-плана;
7. описание продукта или услуги;
8. клиент и рынок;
9. конкуренты;
10. план продаж;
11. стартовые расходы;
12. текущие расходы;
13. расходы на заказ;
14. смета;
15. финансовые расчёты;
16. точка безубыточности;
17. денежный поток;
18. окупаемость;
19. налоговый режим;
20. соцконтракт, если выбран этот режим;
21. риски;
22. недостающие данные;
23. источники;
24. приложения;
25. итоговый статус.

## 9. Структура результата

Бизнес-план должен иметь структурный вид.

Пример верхнего уровня:

```json
{
  "business_plan": {
    "plan_id": "",
    "created_at": "",
    "plan_mode": "social_contract | regular | own_money | grant | loan | unknown",
    "direction_key": "",
    "launch_variant_key": "",
    "city": "",
    "region": "",
    "client_budget": {},
    "status": "complete | partial | insufficient_data | needs_source | needs_price_update",
    "sections": [],
    "calculations": [],
    "sources": [],
    "missing_data": [],
    "risks": [],
    "warnings": [],
    "appendices": []
  }
}
```

Правило:

1. бизнес-план должен иметь статус;
2. бизнес-план должен хранить источники;
3. бизнес-план должен хранить недостающие данные;
4. бизнес-план должен хранить предупреждения;
5. бизнес-план должен хранить режим;
6. бизнес-план должен хранить бюджет клиента.

## 10. Статусы бизнес-плана

Минимальные статусы:

1. `complete` — данных достаточно для чернового бизнес-плана;
2. `partial` — бизнес-план собран, но часть данных неполная;
3. `insufficient_data` — данных не хватает;
4. `needs_source` — нужны источники;
5. `needs_price_update` — нужно обновить цены;
6. `needs_regional_rules` — нужны региональные правила;
7. `blocked_legal` — есть юридический блок;
8. `not_applicable` — режим не применим.

Статус должен быть виден в результате.

Если статус не `complete`, система должна объяснить причину.

## 11. Титульные данные

Титульный блок должен хранить:

1. название плана;
2. режим плана;
3. дату создания;
4. город;
5. регион;
6. направление;
7. вариант запуска;
8. бюджет клиента;
9. статус;
10. версию расчёта;
11. версию шаблона;
12. предупреждение, если данные неполные.

Структура:

```json
{
  "title_block": {
    "title": "",
    "plan_mode": "",
    "created_at": "",
    "city": "",
    "region": "",
    "direction_key": "",
    "launch_variant_key": "",
    "client_budget": {},
    "plan_status": "",
    "calculation_version": "",
    "template_version": "",
    "warnings": []
  }
}
```

## 12. Краткое описание

Краткое описание должно объяснять простыми словами:

1. какое дело планируется;
2. какие услуги будут оказываться;
3. кому будут оказываться услуги;
4. где будет работать человек;
5. какой бюджет указан;
6. какой режим бизнес-плана выбран;
7. хватает ли данных для оценки.

Краткое описание не должно обещать прибыль.

Пример допустимого текста:

`План описывает запуск услуги по сборке мебели в городе. Расчёты сделаны по доступным данным. Часть цен требует обновления.`

Пример недопустимого текста:

`Бизнес точно будет прибыльным и быстро окупится.`

## 13. Направление и услуги

Блок направления должен брать данные из базы направлений.

Он должен содержать:

1. ключ направления;
2. русское название;
3. профессию;
4. специальность;
5. список услуг;
6. вариант запуска;
7. статус направления;
8. уровень доверия;
9. дату обновления;
10. источники.

Если направление имеет статус черновика, это должно быть указано.

Если направление не имеет статуса `ready_for_user_flow`, его нельзя выдавать как готовую рекомендацию.

## 14. Данные пользователя

Блок данных пользователя должен хранить только то, что пользователь сообщил или подтвердил.

Примеры данных:

1. город;
2. регион;
3. бюджет;
4. желаемый режим плана;
5. опыт;
6. ограничения;
7. наличие помещения;
8. наличие автомобиля;
9. готовность работать с клиентами;
10. желаемый формат работы.

Если данные не подтверждены пользователем, не записывать их как факт.

## 15. Блок бюджета

Блок бюджета должен показывать:

1. какой бюджет ввёл пользователь;
2. тип бюджета;
3. минимальный бюджет направления;
4. нормальный бюджет направления;
5. расширенный бюджет направления;
6. хватает ли бюджета;
7. сколько не хватает, если не хватает;
8. какие расходы входят в бюджет;
9. какие расходы не входят;
10. какие цены устарели.

Структура:

```json
{
  "budget_section": {
    "client_budget": {},
    "minimum_start_rub": null,
    "recommended_start_rub": null,
    "expanded_start_rub": null,
    "budget_fit": {},
    "missing_budget_amount_rub": null,
    "budget_warnings": [],
    "source_evidence": []
  }
}
```

## 16. Описание продукта или услуги

Блок должен описывать, что продаётся.

Он должен содержать:

1. список услуг;
2. описание услуг;
3. клиентский тип;
4. способ оказания;
5. место оказания;
6. ограничения;
7. источники.

Если услуги не определены, бизнес-план должен иметь статус `insufficient_data`.

## 17. Клиент и рынок

Блок клиента и рынка должен содержать:

1. кто клиент;
2. город или регион;
3. рыночные сигналы;
4. источники рыночных сигналов;
5. дату сбора;
6. уровень доверия;
7. предупреждения.

Рыночный сигнал не равен доказанному спросу.

Нельзя писать "спрос высокий" без источника.

Если рынок не проверен, писать:

`недостаточно данных`

## 18. Конкуренты

Блок конкурентов должен содержать:

1. количество найденных предложений, если есть;
2. диапазон цен конкурентов;
3. город;
4. дату сбора;
5. источники;
6. ограничения качества данных;
7. вывод, если он подтверждён фактами.

Нельзя делать уверенный вывод о конкуренции по одному слабому источнику.

## 19. План продаж

План продаж должен строиться из данных.

Он должен содержать:

1. услугу;
2. цену услуги;
3. ожидаемое количество заказов;
4. источник цены;
5. источник прогноза заказов;
6. сценарий;
7. уровень доверия;
8. недостающие данные.

Если количества заказов нет, прогноз продаж должен быть неполным.

Нельзя придумывать количество заказов.

## 20. Стартовые расходы

Блок стартовых расходов должен содержать построчную смету.

Структура:

```json
{
  "startup_costs_section": {
    "items": [
      {
        "item": "",
        "category": "",
        "amount_rub": null,
        "quantity": null,
        "required": true,
        "variant_key": "",
        "source_evidence": [],
        "last_checked_at": null,
        "freshness_status": ""
      }
    ],
    "total_startup_costs_rub": null,
    "calculation_status": "calculated | insufficient_data | needs_price_update"
  }
}
```

Правила:

1. нельзя писать одну сумму без расшифровки;
2. каждая позиция должна иметь источник;
3. цены должны иметь дату;
4. устаревшие цены должны быть помечены;
5. обязательные и желательные расходы должны быть разделены.

## 21. Текущие расходы

Блок текущих расходов должен содержать расходы в месяц.

Структура:

```json
{
  "monthly_fixed_costs_section": {
    "items": [],
    "total_monthly_fixed_costs_rub": null,
    "calculation_status": "calculated | insufficient_data | needs_source"
  }
}
```

Примеры:

1. аренда;
2. связь;
3. реклама;
4. сервисы;
5. транспорт;
6. обслуживание оборудования;
7. прочее.

## 22. Расходы на заказ

Блок расходов на заказ должен показывать переменные расходы.

Структура:

```json
{
  "variable_costs_section": {
    "items": [],
    "variable_cost_per_order_rub": null,
    "calculation_status": "calculated | insufficient_data | needs_source"
  }
}
```

Если расходов на заказ нет, точка безубыточности будет неполной.

## 23. Смета

Смета должна быть отдельным блоком.

Для соцконтракта смета особенно важна.

Смета должна содержать:

1. позицию;
2. количество;
3. цену;
4. сумму;
5. источник;
6. допустимость для режима;
7. обязательность;
8. дату цены;
9. статус актуальности;
10. заметки.

Структура:

```json
{
  "estimate_section": {
    "items": [
      {
        "item": "",
        "quantity": null,
        "unit_price_rub": null,
        "total_rub": null,
        "eligible_for_social_contract": null,
        "required": true,
        "source_evidence": [],
        "last_checked_at": null,
        "notes": ""
      }
    ],
    "total_estimate_rub": null,
    "status": "complete | partial | insufficient_data"
  }
}
```

## 24. Финансовые расчёты

Блок финансовых расчётов должен содержать:

1. выручку;
2. постоянные расходы;
3. переменные расходы;
4. прибыль до налога;
5. налог;
6. прибыль после налога;
7. точку безубыточности;
8. окупаемость;
9. денежный поток;
10. сценарии.

Если данных нет, блок должен показать недостающие данные.

## 25. Выручка

Выручка считается только если есть цена и количество заказов.

Формула:

`выручка = цена услуги × количество заказов`

Если нет цены или количества заказов, выручку считать нельзя.

## 26. Точка безубыточности

Точка безубыточности должна считаться по формуле:

`точка безубыточности в заказах = постоянные расходы / (цена услуги - переменные расходы на заказ)`

Если данных не хватает, писать:

`недостаточно данных`

Если цена меньше или равна переменным расходам, модель не выходит в ноль.

## 27. Окупаемость

Окупаемость можно считать только если есть:

1. стартовые расходы;
2. прибыль после налога или прибыль до налога, если налог неизвестен;
3. статус расчёта.

Формула:

`окупаемость в месяцах = стартовые расходы / ежемесячная прибыль`

Если прибыль меньше или равна нулю, окупаемость невозможна по этой модели.

Окупаемость нельзя обещать.

## 28. Денежный поток

Денежный поток должен показывать движение денег по месяцам.

Он должен содержать:

1. месяц;
2. приход денег;
3. расход денег;
4. чистый поток;
5. остаток денег на конец месяца;
6. предупреждения;
7. статус расчёта.

Денежный поток нельзя заменять прибылью.

## 29. Сценарии

Бизнес-план должен поддерживать сценарии.

Минимальные сценарии:

1. осторожный;
2. обычный;
3. сильный.

Сценарии должны отличаться входными данными:

1. цена услуги;
2. количество заказов;
3. расходы;
4. реклама;
5. загрузка;
6. стартовый бюджет.

Сценарии не должны быть фантазиями.

## 30. Налоговый режим

Блок налогов должен содержать:

1. выбранный или предполагаемый режим;
2. НПД, ИП или неизвестно;
3. лимит НПД;
4. риск превышения лимита;
5. риск работников;
6. риск перепродажи;
7. риск агентской схемы;
8. налоговый расчёт, если данных хватает;
9. источники;
10. статус.

Если налоговый режим неизвестен, расчёт после налога должен быть неполным.

## 31. Блок НПД

Для НПД нужно проверять:

1. лимит 2,4 млн рублей в год;
2. работников;
3. перепродажу;
4. агентские и комиссионные схемы;
5. маркированные товары;
6. другие ограничения, которые нужно подтвердить источником.

Если НПД не подходит, система должна объяснить причину.

## 32. Блок соцконтракта

Если режим бизнес-плана — соцконтракт, нужен отдельный блок.

Блок должен содержать:

1. максимальную сумму поддержки;
2. обучение;
3. допустимые расходы;
4. недопустимые расходы;
5. собственные деньги сверх лимита;
6. региональные правила;
7. отчётность;
8. статус полноты данных;
9. предупреждение, что одобрение не гарантируется.

Структура:

```json
{
  "social_contract_section": {
    "max_support_rub": 350000,
    "training_support_rub": 30000,
    "startup_costs_within_limit": null,
    "own_money_required_rub": null,
    "eligible_expenses": [],
    "ineligible_expenses": [],
    "regional_rules_status": "known | missing | needs_source",
    "approval_not_guaranteed": true,
    "status": "complete | partial | insufficient_data"
  }
}
```

## 33. Риски

Блок рисков должен содержать:

1. юридические риски;
2. налоговые риски;
3. рыночные риски;
4. бюджетные риски;
5. риски навыков;
6. сезонность;
7. риски помещения;
8. риски данных;
9. риски устаревших цен.

Риск должен ссылаться на факты или недостающие данные.

Риск не должен быть голословным.

## 34. Недостающие данные

Бизнес-план должен явно показывать недостающие данные.

Пример:

```json
{
  "missing_data": [
    {
      "field": "service_price",
      "why_needed": "нужно для расчёта выручки и точки безубыточности",
      "recommended_action": "собрать цены услуг по городу",
      "severity": "high"
    }
  ]
}
```

Если недостающие данные критические, бизнес-план не должен иметь статус `complete`.

## 35. Источники

Блок источников должен содержать все источники, использованные в плане.

Для каждого источника:

1. источник;
2. ссылка;
3. дата;
4. тип;
5. уровень доверия;
6. что извлекли;
7. город или регион;
8. статус.

Источник должен быть связан с фактами и расчётами.

## 36. Приложения

Приложения могут содержать:

1. полную смету;
2. таблицу расходов;
3. таблицу источников;
4. расчёты;
5. рыночные факты;
6. предупреждения;
7. список недостающих данных.

Приложения не должны содержать выдуманные данные.

## 37. Предупреждения

Бизнес-план должен показывать предупреждения.

Примеры предупреждений:

1. цены устарели;
2. не найден источник по услуге;
3. не найден источник по оборудованию;
4. не найдены региональные правила;
5. нет данных по расходам на заказ;
6. не проверен налоговый режим;
7. не хватает данных для точки безубыточности;
8. направление пока черновое;
9. расчёт имеет низкое доверие.

## 38. Итоговый блок

Итоговый блок должен содержать:

1. статус бизнес-плана;
2. можно ли использовать как черновик;
3. чего не хватает;
4. главные риски;
5. нужно ли обновить цены;
6. нужно ли собрать источники;
7. можно ли продолжать;
8. что будет следующим шагом.

Итоговый блок не должен обещать прибыль или одобрение.

## 39. Пользовательский текст

Пользовательский текст должен быть простым.

Но простой текст не должен скрывать отсутствие данных.

Допустимо:

`По текущим данным можно собрать черновой бизнес-план, но не хватает подтверждённых цен расходников.`

Недопустимо:

`Бизнес прибыльный, можно запускать.`

## 40. Машинный результат

Помимо текста для пользователя, система должна сохранять машинный результат.

Машинный результат нужен для:

1. проверки;
2. пересчёта;
3. истории;
4. смены ИИ;
5. повторного выпуска плана;
6. обновления цен.

Машинный результат должен хранить факты, расчёты, источники, выводы и недостающие данные.

## 41. Структура блока бизнес-плана

Каждый блок бизнес-плана должен иметь структуру:

```json
{
  "section": {
    "section_key": "",
    "title_ru": "",
    "status": "complete | partial | insufficient_data | not_applicable",
    "text": "",
    "facts_used": [],
    "calculations_used": [],
    "sources_used": [],
    "missing_data": [],
    "warnings": [],
    "confidence": "low | medium | high | unknown"
  }
}
```

Правила:

1. каждый блок должен иметь статус;
2. каждый блок должен иметь источники, если использует факты;
3. каждый блок должен иметь предупреждения, если данные слабые;
4. блок без данных не должен выглядеть как готовый.

## 42. Формат для соцконтракта

Для соцконтракта бизнес-план должен дополнительно иметь:

1. блок цели соцконтракта;
2. блок расходов по поддержке;
3. блок собственных средств, если нужны;
4. блок региональных правил;
5. блок отчётности;
6. блок ожидаемого дохода;
7. блок рисков;
8. предупреждение, что одобрение не гарантировано.

Если региональные правила отсутствуют, статус должен быть `needs_regional_rules`.

## 43. Формат обычного бизнес-плана

Обычный бизнес-план должен дополнительно иметь:

1. гибкий бюджет;
2. сценарии;
3. более широкий список расходов;
4. прогноз денег;
5. окупаемость;
6. источники;
7. риски;
8. недостающие данные.

Обычный бизнес-план может быть сделан на бюджет больше 350 000 рублей.

## 44. Формат бизнес-плана с неизвестным бюджетом

Если бюджет неизвестен, система должна:

1. не придумывать бюджет;
2. показать минимальный запуск, если данные есть;
3. показать нормальный запуск, если данные есть;
4. показать расширенный запуск, если данные есть;
5. показать, каких цен не хватает;
6. показать, какие данные нужно собрать;
7. не выдавать итог "бюджета хватает".

## 45. Уровень доверия бизнес-плана

Бизнес-план должен иметь уровень доверия.

Минимальные уровни:

1. `low`;
2. `medium`;
3. `high`;
4. `unknown`.

Уровень доверия зависит от:

1. полноты источников;
2. свежести цен;
3. полноты расходов;
4. полноты рынка;
5. юридической проверки;
6. проверки соцконтракта;
7. качества расчётов;
8. отсутствия противоречий.

Бизнес-план с низким доверием не должен выглядеть как финальный.

## 46. Версия бизнес-плана

Бизнес-план должен иметь версию.

Нужно хранить:

1. версию шаблона;
2. версию расчёта;
3. версию базы;
4. дату создания;
5. дату обновления;
6. роль составителя;
7. инструмент составителя;
8. модель, если использовалась;
9. источники.

## 47. Повторный выпуск бизнес-плана

Если цены обновились, бизнес-план можно пересобрать.

При повторном выпуске нужно:

1. сохранить старую версию;
2. создать новую версию;
3. показать, что изменилось;
4. пересчитать расчёты;
5. обновить статус;
6. сохранить дату.

Старый бизнес-план нельзя silently перезаписывать без истории.

## 48. Что делать при устаревших ценах

Если цены устарели:

1. бизнес-план получает предупреждение;
2. расчёт доверия снижается;
3. статус может стать `needs_price_update`;
4. пользовательский результат должен показать риск;
5. система должна предложить обновить цены.

## 49. Что делать при недостатке источников

Если источников не хватает:

1. бизнес-план не должен быть `complete`;
2. нужно указать недостающие источники;
3. нужно указать, зачем они нужны;
4. нужно указать, какие блоки зависят от них;
5. нужно не придумывать данные.

## 50. Что делать при юридическом блоке

Если есть юридический блок:

1. бизнес-план не должен выдавать направление как готовое;
2. нужно объяснить риск;
3. нужно указать источник риска;
4. нужно поставить статус `blocked_legal` или `partial`;
5. нужно предложить, какие данные нужны для уточнения.

## 51. Проверка перед выдачей бизнес-плана

Перед выдачей бизнес-плана проверить:

1. есть ли направление;
2. направление не черновое для пользовательского режима;
3. есть ли услуги;
4. есть ли бюджет;
5. есть ли стартовые расходы;
6. есть ли текущие расходы;
7. есть ли расходы на заказ или причина их отсутствия;
8. есть ли цены услуг;
9. есть ли источники;
10. свежие ли цены;
11. есть ли налоговая проверка;
12. есть ли проверка соцконтракта, если режим соцконтракт;
13. есть ли предупреждения;
14. нет ли обещаний прибыли;
15. нет ли обещания одобрения соцконтракта.

## 52. Проверка текста

Текст бизнес-плана должен проходить проверку.

Запрещённые формулировки:

1. `гарантированная прибыль`;
2. `точно одобрят`;
3. `бизнес обязательно окупится`;
4. `рисков нет`;
5. `спрос высокий`, если нет источника;
6. `конкуренции нет`, если нет источника;
7. `цены актуальны`, если нет даты проверки.

## 53. Связь с ролями ИИ

Бизнес-план может собирать отдельная роль:

`составитель бизнес-плана`

Эта роль должна быть заменяемой.

Она может работать:

1. через командную строку;
2. через API.

Она не должна придумывать данные.

Она должна брать данные из структурных входов.

## 54. Вход составителя бизнес-плана

Вход:

```json
{
  "business_plan_writer_task": {
    "task_id": "",
    "direction_key": "",
    "launch_variant_key": "",
    "city": "",
    "region": "",
    "plan_mode": "",
    "client_budget": {},
    "facts": [],
    "sources": [],
    "calculations": [],
    "conclusions": [],
    "template_version": "",
    "rules": []
  }
}
```

## 55. Выход составителя бизнес-плана

Выход:

```json
{
  "business_plan_writer_result": {
    "task_id": "",
    "status": "complete | partial | insufficient_data | failed",
    "business_plan": {},
    "missing_data": [],
    "warnings": [],
    "errors": [],
    "sources_used": [],
    "created_at": ""
  }
}
```

## 56. Ошибки составителя бизнес-плана

Ошибки должны храниться.

Примеры ошибок:

1. нет направления;
2. направление не готово;
3. нет бюджета;
4. нет цен услуг;
5. нет расходов;
6. нет источников;
7. цены устарели;
8. юридический блок;
9. не хватает региональных правил;
10. модель не смогла собрать текст.

Структура:

```json
{
  "business_plan_error": {
    "error_type": "",
    "message": "",
    "recoverable": true,
    "next_step": "",
    "created_at": ""
  }
}
```
