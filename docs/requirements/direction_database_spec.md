# Описание базы направлений

## 1. Назначение документа

Этот документ описывает, как должна быть устроена база профессий, специальностей, услуг, направлений и вариантов запуска.

Документ нужен для будущей разработки.

Этот документ не является кодом.

Этот документ не меняет текущую базу.

Этот документ не создаёт финальную базу.

Этот документ фиксирует требования к будущей структуре базы, чтобы исполнители не придумывали поля, статусы и связи из головы.

## 2. Главный принцип базы

База направлений — центральная часть системы.

Система не должна каждый раз придумывать направление заново.

Сначала система должна обращаться к базе.

Если направления нет в базе, система не должна сразу использовать его в пользовательском подборе.

Новое направление сначала должно попасть в кандидаты, пройти сбор источников, проверку, расчёты и только потом стать рабочим направлением.

## 3. Что база должна решать

База должна отвечать на вопросы:

1. что это за направление;
2. какая профессия или специальность лежит в основе;
3. какие услуги можно продавать;
4. кому эти услуги продаются;
5. где это можно делать;
6. какой стартовый бюджет нужен;
7. подходит ли направление под соцконтракт;
8. подходит ли направление под обычный бизнес-план;
9. можно ли работать как самозанятый;
10. нужен ли ИП;
11. есть ли юридические ограничения;
12. какие нужны инструменты, оборудование и материалы;
13. какие есть стартовые расходы;
14. какие есть текущие расходы;
15. какие есть расходы на один заказ;
16. какие цены услуг известны;
17. какие источники подтверждают данные;
18. когда данные обновлялись;
19. хватает ли данных для расчёта;
20. можно ли направление использовать в пользовательском процессе.

## 4. Уровни базы

База должна быть разделена на уровни.

### 4.1. Сырой уровень источников

Сюда попадают данные из внешних и внутренних источников:

1. классификаторы;
2. профессиональные стандарты;
3. правила самозанятости;
4. правила соцконтракта;
5. источники цен услуг;
6. источники цен оборудования;
7. источники рынка;
8. источники закупок.

Сырой уровень нельзя напрямую показывать пользователю.

### 4.2. Уровень связки источников

На этом уровне источники связываются с возможными направлениями.

Пример текущего состояния:

1. есть `source_bridge_candidates.json`;
2. есть `source_bridge_review.json`;
3. есть 13 направлений-кандидатов после связки;
4. 10 направлений приняты для черновой базы;
5. 3 направления отложены.

### 4.3. Уровень черновой базы

На этом уровне направление уже имеет ключ, описание и начальные поля.

Текущий пример:

`business_direction_catalog_draft_v0.json`

Сейчас это черновик.

Это не финальная база.

### 4.4. Уровень рабочей базы

Рабочая база появится позже.

В рабочую базу направление может попасть только если у него есть минимальный набор данных.

Минимальный набор данных описан ниже.

### 4.5. Уровень пользовательского использования

На этом уровне направление можно использовать для подбора и бизнес-плана.

Сейчас этот уровень не создаётся.

Сейчас пользовательские рекомендации не делаются.

## 5. Термины

### 5.1. Профессия

Профессия — это род деятельности человека.

Примеры:

1. парикмахер;
2. мастер маникюра;
3. швея;
4. сборщик мебели;
5. репетитор.

Профессия сама по себе ещё не равна бизнес-направлению.

### 5.2. Специальность

Специальность — более узкая область внутри профессии.

Примеры:

1. мастер по мужским стрижкам;
2. мастер по ремонту одежды;
3. мастер по ремонту бытовой техники;
4. репетитор по математике.

Специальность помогает точнее определить услуги и требования.

### 5.3. Услуга

Услуга — то, что клиент реально покупает.

Примеры:

1. сборка шкафа;
2. генеральная уборка;
3. ремонт молнии;
4. маникюр;
5. стрижка;
6. урок английского.

У направления может быть много услуг.

### 5.4. Направление

Направление — это рабочая единица базы, на основе которой можно в будущем делать подбор и бизнес-план.

Направление должно связывать:

1. профессию;
2. специальность;
3. услуги;
4. вариант запуска;
5. бюджет;
6. ограничения;
7. источники;
8. расчёты.

Пример направления:

`manicure_pedicure`

### 5.5. Вариант запуска

Вариант запуска — конкретный способ начать направление.

Примеры:

1. маникюр на дому;
2. маникюр с выездом к клиенту;
3. маникюр в арендованном кабинете;
4. уборка квартир без машины;
5. уборка квартир с машиной;
6. сборка мебели с базовым инструментом;
7. сборка мебели с расширенным инструментом.

Одно направление может иметь несколько вариантов запуска.

### 5.6. Кандидат

Кандидат — новое направление или специальность, которое ещё не прошло проверку.

Кандидат не должен использоваться для пользовательского бизнес-плана.

### 5.7. Факт

Факт — проверяемая единица данных.

Примеры:

1. цена услуги;
2. цена оборудования;
3. количество объявлений;
4. ссылка на источник;
5. дата сбора;
6. город.

Факт должен хранить источник.

### 5.8. Вывод

Вывод — результат анализа фактов.

Примеры:

1. бюджет подходит;
2. конкуренция высокая;
3. не хватает данных;
4. направление рискованное;
5. нужно обновить цены.

Вывод не должен храниться как факт.

Факт и вывод должны быть разделены.

## 6. Текущие направления

Сейчас в черновой базе есть 10 направлений:

1. `furniture_assembly`
2. `cleaning_services`
3. `clothing_repair_sewing`
4. `shoe_repair`
5. `appliance_repair`
6. `hair_beauty_services`
7. `manicure_pedicure`
8. `tutoring_education`
9. `animal_care`
10. `gardening_plants`

Эти направления пока являются черновыми.

Они не являются финальной базой.

Они не должны прямо показываться пользователю как готовая рекомендация.

## 7. Отложенные направления

Сейчас отложены 3 направления:

1. `bicycle_repair`
2. `photography_video`
3. `sharpening_tools`

Причина:

Для них пока не хватает данных или источников для уверенного включения в рабочую базу.

Эти направления нельзя автоматически переносить в рабочую базу без дополнительной проверки.

## 8. Основная структура записи направления

Каждая запись направления должна иметь примерно такую структуру:

```json
{
  "direction_key": "",
  "title_ru": "",
  "status": "",
  "version": "",
  "created_at": "",
  "updated_at": "",
  "human_readable_summary": "",
  "profession": {},
  "specialties": [],
  "services": [],
  "launch_variants": [],
  "legal_and_tax": {},
  "social_contract": {},
  "budget": {},
  "costs": {},
  "prices": {},
  "market": {},
  "financial_inputs": {},
  "financial_outputs": {},
  "facts": [],
  "conclusions": [],
  "sources": [],
  "refresh_rules": {},
  "quality_gates": {},
  "risks": []
}
```

Это пример структуры, а не готовая финальная схема.

Финальная схема должна быть уточнена позже при разработке.

## 9. Обязательные поля верхнего уровня

Минимальные поля верхнего уровня:

1. `direction_key` — стабильный ключ направления;
2. `title_ru` — русское название;
3. `status` — статус направления;
4. `version` — версия записи;
5. `created_at` — дата создания;
6. `updated_at` — дата изменения;
7. `human_readable_summary` — краткое описание простым языком;
8. `sources` — источники;
9. `facts` — факты;
10. `conclusions` — выводы;
11. `quality_gates` — проверки готовности;
12. `refresh_rules` — правила обновления данных.

## 10. Ключ направления

Ключ направления должен быть стабильным.

Пример:

`manicure_pedicure`

Требования к ключу:

1. латиница;
2. маленькие буквы;
3. слова разделены подчёркиванием;
4. ключ не должен меняться без миграции;
5. ключ не должен зависеть от города;
6. ключ не должен зависеть от бюджета.

Нельзя использовать случайные названия.

## 11. Название направления

Название направления должно быть на русском языке.

Пример:

`Маникюр и педикюр`

Название должно быть понятным пользователю.

Название не должно подменять юридическую проверку.

## 12. Статусы направления

Минимальные статусы:

1. `draft` — черновик;
2. `candidate` — кандидат;
3. `needs_data` — не хватает данных;
4. `needs_source` — не хватает источников;
5. `needs_market_data` — не хватает рыночных данных;
6. `needs_price_update` — нужно обновить цены;
7. `usable_internal` — можно использовать внутри системы;
8. `ready_for_user_flow` — можно использовать в пользовательском процессе;
9. `rejected` — нельзя использовать;
10. `blocked_legal` — юридический риск;
11. `archived` — устарело.

Статусы можно уточнить позже, но смысл должен сохраниться.

## 13. Правило статусов

Пользовательский процесс может использовать только направления со статусом:

`ready_for_user_flow`

Внутренняя аналитика может использовать:

1. `draft`;
2. `candidate`;
3. `needs_data`;
4. `needs_source`;
5. `usable_internal`.

Но такие направления нельзя показывать пользователю как готовую рекомендацию.

## 14. Профессия и специальность

Блок профессии должен хранить:

```json
{
  "profession_title_ru": "",
  "profession_group": "",
  "classification_refs": [],
  "source_evidence": []
}
```

Специальности должны храниться списком:

```json
[
  {
    "specialty_title_ru": "",
    "source_evidence": [],
    "notes": ""
  }
]
```

Если профессия или специальность не подтверждена источником, нужно писать:

`нужно подтвердить источником`

## 15. Услуги

Услуги должны храниться отдельно от профессии.

Пример:

```json
[
  {
    "service_key": "",
    "title_ru": "",
    "description": "",
    "customer_type": "individual | business | mixed | unknown",
    "delivery_mode": "home | client_location | rented_place | online | mixed | unknown",
    "source_evidence": []
  }
]
```

Услуга должна описывать, что именно покупает клиент.

Направление без услуг не готово для бизнес-плана.

## 16. Варианты запуска

Одно направление может иметь несколько вариантов запуска.

Пример структуры:

```json
[
  {
    "variant_key": "",
    "title_ru": "",
    "description": "",
    "location_mode": "home | client_location | rented_place | online | mixed | unknown",
    "transport_required": true,
    "separate_room_required": false,
    "equipment_level": "minimum | recommended | expanded | unknown",
    "budget_profile": {},
    "source_evidence": []
  }
]
```

Примеры вариантов запуска:

1. минимальный запуск;
2. нормальный запуск;
3. расширенный запуск;
4. запуск под соцконтракт;
5. запуск с бюджетом пользователя;
6. запуск с неизвестным бюджетом.

## 17. Бюджет клиента

База должна поддерживать связь направления с бюджетом клиента.

Пользователь в будущем должен уметь указать бюджет:

1. точной суммой: `1 200 000 рублей`;
2. верхней границей: `до 3 000 000 рублей`;
3. диапазоном: `от 500 000 до 1 500 000 рублей`;
4. неизвестным бюджетом.

Структура бюджета клиента:

```json
{
  "budget_input_type": "exact | max | range | unknown",
  "budget_min_rub": null,
  "budget_max_rub": null,
  "budget_exact_rub": null,
  "budget_source": "user_input",
  "budget_purpose": "social_contract | own_money | grant | loan | mixed | unknown"
}
```

Эта структура нужна для будущей разработки.

Сейчас пользовательский подбор по бюджету не создаётся.

## 18. Бюджет направления

Направление должно хранить требования к стартовому капиталу.

Структура:

```json
{
  "capital_requirements": {
    "minimum_start_rub": null,
    "recommended_start_rub": null,
    "expanded_start_rub": null,
    "social_contract_fit_rub": 350000,
    "requires_more_than_social_contract": null,
    "budget_last_checked_at": null,
    "price_sources": []
  }
}
```

Правило:

1. нельзя придумывать суммы;
2. каждая сумма должна иметь источник;
3. если суммы нет, ставить `null`;
4. если нужно подтвердить, писать `нужно подтвердить источником`;
5. если цена устарела, статус должен показывать, что нужно обновление.

## 19. Сравнение бюджета клиента с направлением

Будущая система должна уметь сравнивать бюджет клиента с направлением.

Пример результата:

```json
{
  "budget_fit": {
    "fits_minimum_start": true,
    "fits_recommended_start": false,
    "fits_expanded_start": false,
    "missing_budget_amount_rub": null,
    "budget_risk": "low | medium | high",
    "explanation": ""
  }
}
```

Сейчас эта логика не реализуется.

Сейчас фиксируется требование к будущей системе.

## 20. Юридический и налоговый блок

Каждое направление должно хранить юридические и налоговые ограничения.

Пример структуры:

```json
{
  "legal_and_tax": {
    "npd_possible_preliminary": null,
    "npd_limit_rub_per_year": 2400000,
    "npd_risks": [],
    "ip_required_preliminary": null,
    "employees_required_or_expected": null,
    "resale_risk": null,
    "agency_scheme_risk": null,
    "marked_goods_risk": null,
    "license_or_permit_required": null,
    "legal_notes": "",
    "source_evidence": []
  }
}
```

Правило:

1. нельзя писать, что НПД точно подходит, без проверки;
2. нельзя игнорировать лимит НПД;
3. нельзя игнорировать риск перепродажи;
4. нельзя игнорировать работников;
5. нельзя игнорировать агентские и комиссионные схемы;
6. если данных нет, писать `нужно подтвердить источником`.

## 21. Соцконтракт

Соцконтракт должен быть отдельным блоком.

Пример структуры:

```json
{
  "social_contract": {
    "fit_preliminary": null,
    "max_support_rub": 350000,
    "training_support_rub": 30000,
    "eligible_expense_types": [],
    "restricted_expense_types": [],
    "rent_limit_rule": "нужно подтвердить источником",
    "regional_rules_required": true,
    "reporting_required": true,
    "source_evidence": []
  }
}
```

Правило:

1. соцконтракт — отдельный режим;
2. это не просто обычный бизнес-план с бюджетом 350 000 рублей;
3. нужно учитывать целевые траты;
4. нужно учитывать региональные правила;
5. нужно учитывать отчётность;
6. нужно учитывать ограничения расходов.

## 22. Расходы

Расходы должны делиться на группы.

### 22.1. Стартовые расходы

Стартовые расходы:

1. оборудование;
2. инструменты;
3. материалы;
4. обучение;
5. регистрация;
6. аренда на запуск;
7. реклама на запуск;
8. прочие расходы.

Структура:

```json
{
  "startup_costs": [
    {
      "item": "",
      "category": "",
      "amount_rub": null,
      "required": true,
      "variant_key": "",
      "source_evidence": [],
      "last_checked_at": null
    }
  ]
}
```

### 22.2. Текущие расходы

Текущие расходы:

1. аренда;
2. реклама;
3. связь;
4. сервисы;
5. транспорт;
6. расходники;
7. обслуживание оборудования;
8. прочее.

Структура:

```json
{
  "monthly_fixed_costs": [
    {
      "item": "",
      "amount_rub_per_month": null,
      "source_evidence": [],
      "last_checked_at": null
    }
  ]
}
```

### 22.3. Расходы на заказ

Расходы на заказ:

1. материалы;
2. расходники;
3. доставка;
4. комиссия;
5. упаковка;
6. прочее.

Структура:

```json
{
  "variable_costs_per_order": [
    {
      "item": "",
      "amount_rub_per_order": null,
      "source_evidence": [],
      "last_checked_at": null
    }
  ]
}
```

## 23. Цены услуг

Цены услуг должны храниться как факты.

Структура:

```json
{
  "service_price_facts": [
    {
      "service_key": "",
      "price_rub": null,
      "price_min_rub": null,
      "price_max_rub": null,
      "city": "",
      "source_url": "",
      "source_type": "marketplace | manual_source | official | other",
      "collected_at": "",
      "collector": "",
      "valid_until": "",
      "notes": ""
    }
  ]
}
```

Правило:

1. цена без источника не используется;
2. старая цена должна помечаться как устаревшая;
3. цена должна иметь город или регион, если это важно;
4. диапазон цен лучше одной случайной цены;
5. нельзя придумывать цену.

## 24. Рынок и конкуренты

Рынок и конкуренты должны храниться через факты.

Примеры фактов:

1. количество объявлений;
2. диапазон цен;
3. город;
4. дата;
5. источник;
6. заметки по качеству данных.

Структура:

```json
{
  "market_facts": [
    {
      "fact_type": "listing_count | price_range | competitor_example | demand_signal | other",
      "value": null,
      "city": "",
      "source_url": "",
      "collected_at": "",
      "collector": "",
      "notes": ""
    }
  ]
}
```

Сбор рынка не делается в этом документе.

Документ только фиксирует структуру будущей базы.

## 25. Финансовые входные данные

Финансовые входные данные нужны для расчётов.

Структура:

```json
{
  "financial_inputs": {
    "average_service_price_rub": null,
    "monthly_fixed_costs_rub": null,
    "variable_cost_per_order_rub": null,
    "expected_orders_per_month": null,
    "startup_costs_rub": null,
    "cash_buffer_rub": null,
    "source_evidence": []
  }
}
```

Правило:

1. входные данные должны строиться из фактов;
2. нельзя придумывать среднюю цену;
3. нельзя придумывать ожидаемые заказы;
4. если данных нет, ставить `null`.

## 26. Финансовые выводы

Финансовые выводы должны храниться отдельно от входных данных.

Структура:

```json
{
  "financial_outputs": {
    "break_even_orders_per_month": null,
    "break_even_revenue_rub": null,
    "payback_months": null,
    "budget_fit": {},
    "scenario_results": [],
    "calculated_at": "",
    "calculation_version": "",
    "based_on_facts": []
  }
}
```

Правило:

1. вывод должен ссылаться на факты;
2. вывод можно пересчитать;
3. вывод должен хранить версию расчёта;
4. если данных нет, вывод должен быть `недостаточно данных`.

## 27. Сценарии

Для каждого направления должны быть сценарии.

Минимальные сценарии:

1. осторожный;
2. обычный;
3. сильный.

Структура:

```json
{
  "scenario_results": [
    {
      "scenario_key": "cautious | normal | strong",
      "service_price_rub": null,
      "orders_per_month": null,
      "monthly_revenue_rub": null,
      "monthly_fixed_costs_rub": null,
      "monthly_variable_costs_rub": null,
      "monthly_profit_before_tax_rub": null,
      "break_even_orders_per_month": null,
      "payback_months": null,
      "based_on_facts": [],
      "notes": ""
    }
  ]
}
```

Сценарии не должны быть фантазиями.

Сценарии должны отличаться входными данными.

## 28. Факты

Факт должен храниться отдельно.

Структура факта:

```json
{
  "fact_id": "",
  "fact_type": "",
  "value": null,
  "unit": "",
  "currency": "RUB",
  "city": "",
  "region": "",
  "source_id": "",
  "source_url": "",
  "collected_at": "",
  "collector_role": "",
  "collector_tool": "",
  "model_name": "",
  "prompt_or_task_ref": "",
  "confidence": "low | medium | high",
  "notes": ""
}
```

Правило:

1. факт без источника имеет низкое доверие;
2. факт должен быть проверяемым;
3. факт не должен содержать вывод.

## 29. Выводы

Вывод должен храниться отдельно.

Структура вывода:

```json
{
  "conclusion_id": "",
  "conclusion_type": "",
  "value": "",
  "based_on_facts": [],
  "reason": "",
  "analyst_role": "",
  "analyst_tool": "",
  "model_name": "",
  "created_at": "",
  "confidence": "low | medium | high",
  "notes": ""
}
```

Правило:

1. вывод должен ссылаться на факты;
2. вывод должен объяснять причину;
3. если заменить аналитика, вывод можно пересчитать;
4. вывод без фактов нельзя использовать в пользовательском процессе.

## 30. Источники

Источник должен храниться отдельно.

Структура источника:

```json
{
  "source_id": "",
  "source_type": "official | classifier | marketplace | procurement | article | manual | other",
  "title": "",
  "url": "",
  "accessed_at": "",
  "publisher": "",
  "city": "",
  "region": "",
  "status": "active | unavailable | blocked | stale | unknown",
  "trust_level": "primary | mirror | enrichment | weak | unknown",
  "notes": ""
}
```

Правило:

1. официальный источник лучше зеркала;
2. зеркало должно быть помечено как зеркало;
3. источник может устареть;
4. источник может быть недоступен;
5. источник нельзя считать вечным.

## 31. Обновление данных

Каждое направление должно хранить правила обновления.

Структура:

```json
{
  "refresh_rules": {
    "prices_refresh_days": null,
    "market_refresh_days": null,
    "legal_rules_refresh_days": null,
    "last_full_review_at": null,
    "next_full_review_at": null,
    "stale_if_missing_sources": true
  }
}
```

Правило:

1. цены оборудования устаревают;
2. цены услуг устаревают;
3. правила налогов могут меняться;
4. правила соцконтракта могут меняться;
5. устаревшие данные должны влиять на статус направления.

## 32. Проверки качества

Каждое направление должно проходить проверки качества.

Структура:

```json
{
  "quality_gates": {
    "has_profession_source": false,
    "has_service_list": false,
    "has_legal_tax_check": false,
    "has_social_contract_check": false,
    "has_startup_costs": false,
    "has_service_prices": false,
    "has_market_facts": false,
    "has_break_even_inputs": false,
    "has_source_history": false,
    "ready_for_internal_use": false,
    "ready_for_user_flow": false
  }
}
```

Правило:

1. если нет источника профессии, направление не готово;
2. если нет услуг, направление не готово;
3. если нет цен услуг, направление не готово для бизнес-плана;
4. если нет расходов, направление не готово для бизнес-плана;
5. если нет юридической проверки, направление не готово для пользователя;
6. если нет истории источников, направление не готово для пользователя.

## 33. Риски

Риски должны храниться структурно.

Структура:

```json
{
  "risks": [
    {
      "risk_type": "legal | tax | market | budget | skill | seasonality | location | data_quality | other",
      "level": "low | medium | high | unknown",
      "description": "",
      "based_on_facts": [],
      "mitigation": "",
      "notes": ""
    }
  ]
}
```

Риск не должен быть голословным.

Если риск основан на выводе, нужно хранить причину.

## 34. Кандидаты новых специальностей

Новая специальность должна сначала попадать в кандидаты.

Структура кандидата:

```json
{
  "candidate_key": "",
  "title_ru": "",
  "candidate_source": "",
  "found_at": "",
  "status": "new | collecting_sources | needs_data | ready_for_review | accepted | rejected",
  "profession_hypothesis": "",
  "service_hypotheses": [],
  "required_checks": [],
  "collected_sources": [],
  "notes": ""
}
```

Кандидат не должен использоваться в пользовательском процессе.

## 35. Путь добавления новой специальности

Путь:

1. найден кандидат;
2. создана карточка кандидата;
3. собраны источники по профессии;
4. собраны источники по услугам;
5. собраны цены услуг;
6. собраны цены оборудования;
7. собраны текущие расходы;
8. проверены налоги;
9. проверены ограничения НПД;
10. проверены ограничения ИП;
11. проверены ограничения соцконтракта;
12. посчитаны стартовые траты;
13. посчитана точка безубыточности;
14. сделаны сценарии;
15. поставлен статус;
16. направление принято или отложено.

## 36. Что нельзя делать с базой

Нельзя:

1. добавлять направление без источников;
2. добавлять направление только потому, что его предложил ИИ;
3. использовать направление без услуг;
4. использовать направление без бюджета;
5. использовать направление без цен;
6. использовать направление без проверки НПД/ИП;
7. использовать направление без статуса;
8. использовать старые цены как актуальные;
9. смешивать факт и вывод;
10. показывать пользователю черновик как рекомендацию.

## 37. Что можно делать с черновой базой

Черновую базу можно использовать:

1. для внутренней разработки;
2. для анализа структуры;
3. для наполнения данных;
4. для проверки источников;
5. для подготовки документов.

Черновую базу нельзя использовать:

1. для пользовательского подбора;
2. для обещания прибыли;
3. для финального бизнес-плана;
4. для автоматической рекомендации.

## 38. Отношение к полной базе

Полная сырая база может быть отдельным уровнем.

Она нужна, чтобы не потерять потенциальные направления.

Но полная сырая база не должна напрямую кормить пользовательский процесс.

Рабочий пользовательский процесс должен опираться на безопасную проверенную базу.

## 39. Версионирование

База должна иметь версии.

Нужно хранить:

1. версию схемы;
2. версию записи направления;
3. дату обновления;
4. источник изменения;
5. кто или что изменило;
6. причину изменения.

Если меняется структура, должна быть новая версия схемы.

Если меняются данные, должна быть новая версия записи или история изменения.
