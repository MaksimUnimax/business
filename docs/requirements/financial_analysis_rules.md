# Правила финансовой аналитики

## 1. Назначение документа

Этот документ описывает правила финансовой аналитики для будущей системы подготовки бизнес-планов.

Документ нужен для разработки.

Этот документ не является кодом.

Этот документ не запускает расчёты.

Этот документ не создаёт бизнес-план.

Этот документ фиксирует, какие данные нужны для финансовой оценки направления, какие расчёты допустимы, какие расчёты нельзя делать без данных и как не допустить выдуманных цифр.

## 2. Главный принцип

Финансовая аналитика не должна сочиняться.

Система не должна придумывать:

1. цены услуг;
2. цены оборудования;
3. количество заказов;
4. выручку;
5. прибыль;
6. окупаемость;
7. спрос;
8. конкуренцию;
9. расходы;
10. точку безубыточности.

Если данных нет, система должна писать:

`недостаточно данных`

Если методика или показатель не подтверждены источником, система должна писать:

`нужно подтвердить источником`

## 3. Источники правил

Основные источники для текущего документа:

1. SBA: правила подготовки бизнес-плана;
2. SBA: расчёт точки безубыточности;
3. SBA: расчёт стартовых расходов;
4. SCORE: шаблон финансовых прогнозов малого бизнеса;
5. документы проекта:

   * `docs/requirements/tz_source_basis.md`
   * `docs/requirements/full_tz.md`
   * `docs/requirements/direction_database_spec.md`

Из этих источников берём:

1. необходимость считать стартовые расходы;
2. необходимость считать текущие расходы;
3. необходимость прогнозировать продажи;
4. необходимость считать движение денег;
5. необходимость считать прибыль и убыток;
6. необходимость считать точку безубыточности;
7. необходимость отделять входные данные от выводов;
8. необходимость хранить источники и даты.

## 4. Что должна делать финансовая аналитика

Финансовая аналитика должна отвечать на вопросы:

1. сколько денег нужно для старта;
2. какие расходы обязательные;
3. какие расходы желательные;
4. какие расходы можно отложить;
5. сколько денег нужно каждый месяц;
6. сколько стоит один заказ;
7. какая цена услуги;
8. сколько заказов нужно для выхода в ноль;
9. хватает ли бюджета клиента;
10. какой денежный запас нужен;
11. когда направление может окупиться;
12. какие данные не хватает;
13. какие риски есть в расчёте;
14. можно ли использовать направление для бизнес-плана;
15. можно ли использовать направление в пользовательском процессе.

## 5. Что финансовая аналитика не должна делать

Финансовая аналитика не должна:

1. обещать прибыль;
2. обещать получение соцконтракта;
3. обещать окупаемость;
4. писать "выгодно" без расчёта;
5. писать "спрос высокий" без источника;
6. писать "конкуренция низкая" без источника;
7. брать старые цены как актуальные;
8. использовать цену без даты;
9. использовать цену без источника;
10. использовать вывод как факт;
11. считать точку безубыточности без цены услуги;
12. считать точку безубыточности без расходов;
13. считать окупаемость без стартовых расходов;
14. считать прибыль без выручки и расходов;
15. подставлять средние цифры из головы.

## 6. Основные понятия

## 6.1. Стартовые расходы

Стартовые расходы — это деньги, которые нужны до начала работы или на самом старте.

Примеры:

1. оборудование;
2. инструменты;
3. материалы;
4. обучение;
5. регистрация;
6. аренда на запуск;
7. реклама на запуск;
8. первичная закупка расходников;
9. доставка оборудования;
10. настройка рабочего места.

Стартовые расходы не равны текущим расходам.

## 6.2. Текущие расходы

Текущие расходы — это расходы, которые повторяются каждый месяц.

Примеры:

1. аренда;
2. связь;
3. реклама;
4. сервисы;
5. транспорт;
6. расходники;
7. обслуживание оборудования;
8. интернет;
9. подписки;
10. прочие постоянные платежи.

## 6.3. Расходы на заказ

Расходы на заказ — это расходы, которые возникают при выполнении одного заказа.

Примеры:

1. материалы;
2. расходники;
3. упаковка;
4. доставка;
5. комиссия;
6. одноразовые принадлежности;
7. часть транспортных расходов, если они зависят от заказа.

## 6.4. Цена услуги

Цена услуги — сумма, которую платит клиент за одну услугу или заказ.

Цена услуги должна иметь:

1. источник;
2. город или регион;
3. дату сбора;
4. тип услуги;
5. диапазон, если цена на рынке разная.

## 6.5. Выручка

Выручка — сумма денег, которую бизнес получает от продаж.

Пример:

`выручка = цена услуги × количество заказов`

Если цена услуги или количество заказов неизвестны, выручку считать нельзя.

## 6.6. Прибыль до налога

Прибыль до налога — деньги, которые остаются после расходов до учёта налога.

Пример:

`прибыль до налога = выручка - текущие расходы - переменные расходы`

Если расходы неизвестны, прибыль считать нельзя.

## 6.7. Денежный поток

Денежный поток — движение денег: сколько денег пришло и сколько ушло.

Важно:

1. прибыль и деньги на руках — не одно и то же;
2. заказ может быть выполнен сейчас, а деньги прийти позже;
3. оборудование может быть куплено сразу, а окупаться долго;
4. бизнес может быть прибыльным на бумаге, но испытывать нехватку денег.

Если нет данных по срокам поступлений и платежей, денежный поток должен иметь статус `недостаточно данных`.

## 6.8. Точка безубыточности

Точка безубыточности — уровень продаж, при котором доходы покрывают расходы, но прибыли ещё нет.

Для услуг можно считать количество заказов, нужное для выхода в ноль.

Базовая формула:

`точка безубыточности в заказах = постоянные расходы / (цена услуги - переменные расходы на заказ)`

Если цена услуги меньше или равна переменным расходам на заказ, направление не выходит в ноль по этой модели.

Если нет постоянных расходов, цены услуги или переменных расходов, точку безубыточности считать нельзя.

## 6.9. Окупаемость

Окупаемость — примерный срок, за который стартовые расходы могут вернуться через прибыль.

Пример:

`окупаемость в месяцах = стартовые расходы / ежемесячная прибыль`

Если ежемесячная прибыль меньше или равна нулю, окупаемость считать нельзя.

Если нет стартовых расходов или прибыли, окупаемость считать нельзя.

## 6.10. Денежный запас

Денежный запас — деньги, которые нужны, чтобы пережить первые месяцы без стабильной прибыли.

Денежный запас не должен придумываться из головы.

Если нет подтверждённой методики или данных, нужно писать:

`нужно подтвердить источником`

## 7. Минимальные входные данные для расчёта

Для финансовой оценки направления нужны минимум:

1. город или регион;
2. услуга;
3. цена услуги;
4. диапазон цен услуги;
5. стартовые расходы;
6. текущие расходы в месяц;
7. расходы на один заказ;
8. ожидаемое количество заказов;
9. источник по цене услуги;
10. источник по оборудованию;
11. источник по расходам;
12. дата сбора данных;
13. статус актуальности цены;
14. налоговый режим;
15. ограничения НПД или ИП;
16. режим бизнес-плана: соцконтракт или обычный план;
17. бюджет клиента.

Если любого ключевого блока нет, расчёт должен быть помечен как неполный.

## 8. Структура финансовых входных данных

Финансовые входные данные должны храниться отдельно от выводов.

Пример структуры:

```json
{
  "financial_inputs": {
    "city": "",
    "region": "",
    "service_key": "",
    "average_service_price_rub": null,
    "service_price_min_rub": null,
    "service_price_max_rub": null,
    "monthly_fixed_costs_rub": null,
    "variable_cost_per_order_rub": null,
    "expected_orders_per_month": null,
    "startup_costs_rub": null,
    "cash_buffer_rub": null,
    "tax_mode": "npd | ip | unknown",
    "business_plan_mode": "social_contract | regular | unknown",
    "client_budget": {},
    "source_evidence": []
  }
}
```

Правила:

1. если значения нет, ставить `null`;
2. не подставлять число из головы;
3. каждое число должно ссылаться на источник или факт;
4. если источник слабый, доверие должно быть низким;
5. если цена устарела, расчёт должен быть помечен как рискованный.

## 9. Стартовые расходы

Стартовые расходы должны храниться построчно.

Пример структуры:

```json
{
  "startup_costs": [
    {
      "item": "",
      "category": "equipment | tools | materials | training | rent | advertising | registration | other",
      "amount_rub": null,
      "required": true,
      "variant_key": "",
      "source_evidence": [],
      "last_checked_at": null,
      "notes": ""
    }
  ]
}
```

Правила:

1. каждая строка расхода должна иметь источник;
2. обязательные и желательные расходы нужно разделять;
3. расходы для соцконтракта и обычного запуска могут отличаться;
4. расходы для минимального, нормального и расширенного запуска могут отличаться;
5. если цена устарела, расход нельзя считать актуальным без обновления.

## 10. Категории стартовых расходов

Минимальные категории:

1. оборудование;
2. инструменты;
3. материалы;
4. расходники на старт;
5. обучение;
6. регистрация;
7. аренда на запуск;
8. реклама на запуск;
9. доставка;
10. ремонт или подготовка рабочего места;
11. прочее.

Категории можно уточнять позже, но нельзя смешивать всё в одну сумму без расшифровки.

## 11. Текущие расходы

Текущие расходы должны храниться построчно.

Пример структуры:

```json
{
  "monthly_fixed_costs": [
    {
      "item": "",
      "category": "rent | advertising | communication | service | transport | maintenance | utilities | other",
      "amount_rub_per_month": null,
      "source_evidence": [],
      "last_checked_at": null,
      "notes": ""
    }
  ]
}
```

Правила:

1. текущие расходы не должны смешиваться со стартовыми;
2. расходы должны иметь период;
3. если расход нерегулярный, нужно указать это в заметках;
4. если источник отсутствует, расход не считается подтверждённым.

## 12. Расходы на заказ

Расходы на заказ должны храниться отдельно.

Пример структуры:

```json
{
  "variable_costs_per_order": [
    {
      "item": "",
      "category": "materials | consumables | delivery | commission | packaging | transport | other",
      "amount_rub_per_order": null,
      "source_evidence": [],
      "last_checked_at": null,
      "notes": ""
    }
  ]
}
```

Правила:

1. переменные расходы зависят от количества заказов;
2. без переменных расходов нельзя считать точку безубыточности точно;
3. если переменные расходы неизвестны, расчёт должен быть помечен как неполный;
4. нельзя считать все расходы постоянными.

## 13. Цена услуги

Цена услуги должна храниться как факт.

Пример структуры:

```json
{
  "service_price_facts": [
    {
      "service_key": "",
      "price_rub": null,
      "price_min_rub": null,
      "price_max_rub": null,
      "city": "",
      "region": "",
      "source_url": "",
      "source_type": "marketplace | manual_source | official | other",
      "collected_at": "",
      "collector": "",
      "valid_until": "",
      "confidence": "low | medium | high",
      "notes": ""
    }
  ]
}
```

Правила:

1. цена без источника не используется;
2. цена без даты не используется как актуальная;
3. цена должна быть привязана к услуге;
4. цена должна быть привязана к городу или региону, если это важно;
5. лучше хранить диапазон цен, а не одну случайную цену.

## 14. Прогноз заказов

Прогноз заказов нельзя придумывать.

Прогноз заказов должен быть основан на:

1. рыночных данных;
2. истории продаж, если она есть;
3. количестве объявлений;
4. спросе;
5. рекламном плане;
6. похожих бизнесах;
7. данных, которые нужно подтвердить источником.

Если источников нет, нужно писать:

`недостаточно данных`

Структура:

```json
{
  "orders_forecast": {
    "expected_orders_per_month": null,
    "forecast_method": "",
    "based_on_facts": [],
    "confidence": "low | medium | high",
    "notes": ""
  }
}
```

## 15. Выручка

Выручка считается только при наличии цены и количества заказов.

Формула:

`выручка = цена услуги × количество заказов`

Структура:

```json
{
  "revenue_calculation": {
    "service_price_rub": null,
    "orders_per_month": null,
    "monthly_revenue_rub": null,
    "based_on_facts": [],
    "calculated_at": "",
    "calculation_version": ""
  }
}
```

Если цена или количество заказов неизвестны, `monthly_revenue_rub` должен быть `null`.

## 16. Постоянные расходы

Постоянные расходы — расходы, которые не зависят напрямую от количества заказов в коротком периоде.

Примеры:

1. аренда;
2. связь;
3. сервисы;
4. реклама;
5. часть транспорта;
6. обслуживание оборудования.

Структура:

```json
{
  "fixed_costs_calculation": {
    "monthly_fixed_costs_rub": null,
    "items": [],
    "based_on_facts": [],
    "calculated_at": "",
    "calculation_version": ""
  }
}
```

## 17. Переменные расходы

Переменные расходы зависят от количества заказов.

Примеры:

1. материалы;
2. расходники;
3. упаковка;
4. доставка;
5. комиссия;
6. расход топлива на заказ, если считается отдельно.

Структура:

```json
{
  "variable_costs_calculation": {
    "variable_cost_per_order_rub": null,
    "orders_per_month": null,
    "monthly_variable_costs_rub": null,
    "items": [],
    "based_on_facts": [],
    "calculated_at": "",
    "calculation_version": ""
  }
}
```

## 18. Точка безубыточности

Точка безубыточности показывает, сколько заказов нужно, чтобы покрыть расходы.

Формула:

`точка безубыточности в заказах = постоянные расходы / (цена услуги - переменные расходы на заказ)`

Структура:

```json
{
  "break_even": {
    "service_price_rub": null,
    "variable_cost_per_order_rub": null,
    "monthly_fixed_costs_rub": null,
    "contribution_margin_rub": null,
    "break_even_orders_per_month": null,
    "break_even_revenue_rub": null,
    "calculation_status": "calculated | insufficient_data | impossible | needs_source",
    "based_on_facts": [],
    "calculated_at": "",
    "calculation_version": ""
  }
}
```

Правила:

1. если цены услуги нет — расчёт невозможен;
2. если переменных расходов нет — расчёт неполный;
3. если постоянных расходов нет — расчёт неполный;
4. если цена услуги меньше или равна переменным расходам — модель не выходит в ноль;
5. если данных нет, писать `недостаточно данных`;
6. нельзя округлять результат так, чтобы скрыть риск.

## 19. Прибыль до налога

Прибыль до налога считается только при наличии выручки и расходов.

Формула:

`прибыль до налога = выручка - постоянные расходы - переменные расходы`

Структура:

```json
{
  "profit_before_tax": {
    "monthly_revenue_rub": null,
    "monthly_fixed_costs_rub": null,
    "monthly_variable_costs_rub": null,
    "monthly_profit_before_tax_rub": null,
    "calculation_status": "calculated | insufficient_data",
    "based_on_facts": [],
    "calculated_at": "",
    "calculation_version": ""
  }
}
```

Правила:

1. прибыль нельзя считать без выручки;
2. прибыль нельзя считать без расходов;
3. прибыль нельзя обещать пользователю;
4. прибыль должна быть показана как расчёт по входным данным, а не как гарантия.

## 20. Налог

Налог зависит от режима.

Минимальные режимы:

1. НПД;
2. ИП;
3. неизвестно;
4. нужно подтвердить.

Для НПД нужно учитывать:

1. лимит дохода 2,4 млн рублей в год;
2. ограничение по работникам;
3. ограничение по перепродаже;
4. ограничение по агентским и комиссионным схемам;
5. другие ограничения, которые нужно подтвердить источником.

Структура:

```json
{
  "tax_calculation": {
    "tax_mode": "npd | ip | unknown | needs_source",
    "tax_rate_percent": null,
    "monthly_tax_rub": null,
    "annual_revenue_rub": null,
    "npd_limit_rub_per_year": 2400000,
    "npd_limit_exceeded": null,
    "calculation_status": "calculated | insufficient_data | needs_source",
    "based_on_facts": [],
    "notes": ""
  }
}
```

Правила:

1. налог нельзя считать, если режим неизвестен;
2. если НПД не подходит, нужно объяснить причину;
3. если доход превышает лимит НПД, направление или сценарий должен получить риск;
4. ставка налога должна иметь источник или пометку `нужно подтвердить источником`.

## 21. Прибыль после налога

Прибыль после налога можно считать только если известен налог.

Формула:

`прибыль после налога = прибыль до налога - налог`

Структура:

```json
{
  "profit_after_tax": {
    "monthly_profit_before_tax_rub": null,
    "monthly_tax_rub": null,
    "monthly_profit_after_tax_rub": null,
    "calculation_status": "calculated | insufficient_data | needs_source",
    "based_on_facts": [],
    "notes": ""
  }
}
```

Если налог неизвестен, прибыль после налога должна быть `null`.

## 22. Окупаемость

Окупаемость можно считать только при наличии стартовых расходов и прибыли.

Формула:

`окупаемость в месяцах = стартовые расходы / ежемесячная прибыль`

Структура:

```json
{
  "payback": {
    "startup_costs_rub": null,
    "monthly_profit_after_tax_rub": null,
    "payback_months": null,
    "calculation_status": "calculated | insufficient_data | impossible",
    "based_on_facts": [],
    "notes": ""
  }
}
```

Правила:

1. если стартовые расходы неизвестны — окупаемость считать нельзя;
2. если прибыль неизвестна — окупаемость считать нельзя;
3. если прибыль меньше или равна нулю — окупаемость невозможна по этой модели;
4. окупаемость нельзя обещать;
5. окупаемость должна показываться как расчётный сценарий.

## 23. Денежный поток

Денежный поток показывает, как деньги приходят и уходят по месяцам.

Структура:

```json
{
  "cash_flow": {
    "months": [
      {
        "month_number": 1,
        "cash_in_rub": null,
        "cash_out_rub": null,
        "net_cash_flow_rub": null,
        "cash_balance_end_rub": null,
        "notes": ""
      }
    ],
    "calculation_status": "calculated | insufficient_data",
    "based_on_facts": [],
    "notes": ""
  }
}
```

Правила:

1. денежный поток нельзя заменять прибылью;
2. стартовые траты должны попадать в первые месяцы;
3. если нет данных по срокам поступлений и расходов, расчёт должен быть неполным;
4. отрицательный денежный остаток должен показывать риск.

## 24. Денежный запас

Денежный запас нужен для покрытия первых месяцев.

Структура:

```json
{
  "cash_buffer": {
    "recommended_cash_buffer_rub": null,
    "months_covered": null,
    "method": "needs_source",
    "calculation_status": "needs_source | calculated | insufficient_data",
    "based_on_facts": [],
    "notes": ""
  }
}
```

Правило:

1. денежный запас нельзя придумывать;
2. методика должна иметь источник;
3. если методики нет, писать `нужно подтвердить источником`.

## 25. Сценарии

Для каждого направления нужно считать несколько сценариев.

Минимальные сценарии:

1. осторожный;
2. обычный;
3. сильный.

Структура:

```json
{
  "scenario_results": [
    {
      "scenario_key": "cautious | normal | strong",
      "service_price_rub": null,
      "orders_per_month": null,
      "monthly_revenue_rub": null,
      "monthly_fixed_costs_rub": null,
      "monthly_variable_costs_rub": null,
      "monthly_profit_before_tax_rub": null,
      "monthly_profit_after_tax_rub": null,
      "break_even_orders_per_month": null,
      "payback_months": null,
      "cash_flow_status": "",
      "based_on_facts": [],
      "confidence": "low | medium | high",
      "notes": ""
    }
  ]
}
```

Правила:

1. сценарии должны отличаться входными данными;
2. сценарии не должны быть фантазиями;
3. каждый сценарий должен иметь источники;
4. каждый сценарий должен иметь уровень доверия;
5. если нет данных, сценарий должен быть неполным.

## 26. Бюджет клиента

Финансовая аналитика должна учитывать бюджет клиента.

Пользователь может указать бюджет:

1. точной суммой: `1 200 000 рублей`;
2. верхней границей: `до 3 000 000 рублей`;
3. диапазоном: `от 500 000 до 1 500 000 рублей`;
4. неизвестным бюджетом.

Структура:

```json
{
  "client_budget": {
    "budget_input_type": "exact | max | range | unknown",
    "budget_min_rub": null,
    "budget_max_rub": null,
    "budget_exact_rub": null,
    "budget_source": "user_input",
    "budget_purpose": "social_contract | own_money | grant | loan | mixed | unknown"
  }
}
```

## 27. Сравнение бюджета клиента с направлением

Система должна уметь сравнить бюджет клиента с требованиями направления.

Структура:

```json
{
  "budget_fit": {
    "fits_minimum_start": null,
    "fits_recommended_start": null,
    "fits_expanded_start": null,
    "missing_budget_amount_rub": null,
    "budget_risk": "low | medium | high | unknown",
    "calculation_status": "calculated | insufficient_data",
    "explanation": ""
  }
}
```

Правила:

1. если бюджет точный, сравнивать точную сумму;
2. если бюджет "до суммы", считать верхнюю границу;
3. если бюджет диапазоном, учитывать минимум и максимум;
4. если бюджет неизвестен, не делать вывод о соответствии;
5. нельзя предлагать направление как подходящее, если стартовые расходы неизвестны.

## 28. Соцконтракт

Финансовая аналитика для соцконтракта должна учитывать:

1. лимит поддержки;
2. целевые траты;
3. обучение;
4. ограничения расходов;
5. региональные правила;
6. отчётность;
7. требование показать доход;
8. регистрацию самозанятого или ИП.

Структура:

```json
{
  "social_contract_finance": {
    "max_support_rub": 350000,
    "training_support_rub": 30000,
    "startup_costs_within_limit": null,
    "own_money_required_rub": null,
    "eligible_expenses_rub": null,
    "ineligible_expenses_rub": null,
    "regional_rules_required": true,
    "calculation_status": "calculated | insufficient_data | needs_regional_rules",
    "based_on_facts": [],
    "notes": ""
  }
}
```

Правила:

1. соцконтракт — отдельный режим;
2. это не просто обычный бизнес-план с бюджетом 350 000 рублей;
3. если региональные правила неизвестны, результат должен быть неполным;
4. нельзя обещать одобрение соцконтракта;
5. нельзя включать недопустимые расходы без проверки.

## 29. Обычный бизнес-план

Для обычного бизнес-плана бюджет может быть больше 350 000 рублей.

Финансовая аналитика должна учитывать:

1. бюджет клиента;
2. оборудование;
3. помещение;
4. рекламу;
5. стартовые расходы;
6. текущие расходы;
7. налоговый режим;
8. сценарии;
9. окупаемость;
10. денежный поток.

Обычный бизнес-план не должен автоматически наследовать ограничения соцконтракта, если режим не соцконтракт.

## 30. Проверка НПД

Для НПД нужно проверять:

1. лимит дохода;
2. работников;
3. перепродажу чужих товаров;
4. агентские схемы;
5. комиссионные схемы;
6. маркированные товары;
7. другие ограничения, которые нужно подтвердить источником.

Структура:

```json
{
  "npd_check": {
    "npd_possible_preliminary": null,
    "annual_revenue_rub": null,
    "npd_limit_rub_per_year": 2400000,
    "npd_limit_exceeded": null,
    "employees_risk": null,
    "resale_risk": null,
    "agency_scheme_risk": null,
    "marked_goods_risk": null,
    "calculation_status": "checked | insufficient_data | needs_source",
    "source_evidence": [],
    "notes": ""
  }
}
```

Если НПД не подходит, система должна объяснить почему.

## 31. Уровень доверия

Каждый расчёт должен иметь уровень доверия.

Минимальные уровни:

1. `low`;
2. `medium`;
3. `high`;
4. `unknown`.

Уровень доверия зависит от:

1. количества источников;
2. качества источников;
3. свежести данных;
4. полноты расходов;
5. полноты цен услуг;
6. наличия рынка;
7. наличия юридической проверки.

Расчёт с низким доверием нельзя выдавать как уверенный результат.

## 32. Статусы расчёта

Минимальные статусы:

1. `calculated` — рассчитано;
2. `insufficient_data` — недостаточно данных;
3. `needs_source` — нужен источник;
4. `needs_price_update` — нужно обновить цены;
5. `impossible` — невозможно по модели;
6. `blocked_legal` — юридический блок;
7. `not_applicable` — не применимо.

Статус должен храниться вместе с расчётом.

## 33. Запрет на скрытые допущения

Система не должна делать скрытые допущения.

Если используется допущение, оно должно быть явно записано.

Структура:

```json
{
  "assumptions": [
    {
      "assumption_key": "",
      "description": "",
      "why_needed": "",
      "source_evidence": [],
      "confidence": "low | medium | high",
      "notes": ""
    }
  ]
}
```

Если допущение не подтверждено источником, оно не должно превращаться в факт.

## 34. Проверка расчёта

Каждый расчёт должен хранить:

1. входные данные;
2. формулу;
3. версию расчёта;
4. дату расчёта;
5. список фактов;
6. список допущений;
7. статус;
8. уровень доверия.

Структура:

```json
{
  "calculation_audit": {
    "calculation_id": "",
    "calculation_type": "",
    "input_refs": [],
    "fact_refs": [],
    "assumption_refs": [],
    "formula_ref": "",
    "calculation_version": "",
    "calculated_at": "",
    "calculated_by_role": "",
    "calculated_by_tool": "",
    "status": "",
    "confidence": "",
    "notes": ""
  }
}
```

## 35. Формулы

Формулы должны храниться отдельно или быть явно указаны.

Минимальные формулы:

1. выручка;
2. переменные расходы за месяц;
3. прибыль до налога;
4. прибыль после налога;
5. точка безубыточности;
6. окупаемость.

Пример структуры:

```json
{
  "formula_refs": [
    {
      "formula_key": "break_even_orders",
      "title_ru": "Точка безубыточности в заказах",
      "formula_text": "monthly_fixed_costs / (service_price - variable_cost_per_order)",
      "source_evidence": [],
      "notes": ""
    }
  ]
}
```

Если формула не подтверждена источником, писать:

`нужно подтвердить источником`

## 36. Нельзя смешивать факт и вывод

Пример факта:

`цена услуги 2500 рублей`

Пример вывода:

`цена находится в среднем диапазоне`

Пример расчёта:

`при 40 заказах выручка составит 100 000 рублей`

Эти три вещи должны храниться отдельно.

## 37. Связь с базой направлений

Финансовая аналитика должна брать данные из базы направлений.

Она не должна создавать направление заново.

Если направления нет в базе, нужно создать кандидата, а не считать бизнес-план сразу.

## 38. Связь с источниками

Финансовая аналитика должна ссылаться на источники.

Источники должны хранить:

1. ссылку;
2. дату;
3. город;
4. тип источника;
5. уровень доверия;
6. статус источника.

Если источник недоступен, расчёт должен показать риск.

## 39. Что делать, если данных не хватает

Если данных не хватает, система должна:

1. указать, каких данных не хватает;
2. не считать невозможный показатель;
3. не подставлять средние значения из головы;
4. поставить статус `insufficient_data`;
5. предложить, какие данные нужно собрать.

Пример:

```json
{
  "missing_data": [
    "service_price",
    "variable_cost_per_order",
    "monthly_fixed_costs"
  ],
  "result": "недостаточно данных"
}
```

## 40. Что делать, если цена устарела

Если цена устарела, система должна:

1. пометить цену как устаревшую;
2. не использовать её как актуальную без предупреждения;
3. поставить статус `needs_price_update`;
4. показать дату последнего сбора;
5. указать, какой источник нужно обновить.

## 41. Что делать, если источник слабый

Если источник слабый, система должна:

1. снизить доверие;
2. показать источник;
3. не делать уверенный вывод;
4. пометить расчёт как рискованный;
5. предложить собрать более сильный источник.

## 42. Что делать, если расчёт невозможен

Если расчёт невозможен, система должна не заменять его текстом "примерно".

Она должна указать:

1. какой расчёт невозможен;
2. почему невозможен;
3. какие данные нужны;
4. какие источники нужно собрать.

## 43. Минимальный результат финансовой аналитики

Минимальный результат по направлению должен содержать:

1. статус расчёта;
2. стартовые расходы;
3. текущие расходы;
4. расходы на заказ;
5. цену услуги;
6. точку безубыточности или причину невозможности;
7. бюджетное соответствие;
8. риски;
9. недостающие данные;
10. источники;
11. дату расчёта;
12. уровень доверия.

## 44. Результат для пользователя

Пользовательский результат должен быть простым.

Но простой результат не должен скрывать отсутствие данных.

Пример допустимого вывода:

`По текущим данным направление нельзя оценить точно: не хватает цен расходников и подтверждённой цены услуги в вашем городе.`

Пример недопустимого вывода:

`Это прибыльное направление, можно запускать.`

## 45. Автоматизация

Финансовая аналитика должна быть автоматизированной.

Человек не должен быть обязательной частью клиентского процесса.

Ручная проверка может использоваться внутри команды только для улучшения базы, проверки спорных направлений и настройки правил.

## 46. Заменяемый аналитик

Аналитик должен быть заменяемым.

Сегодня аналитиком может быть MiMo.

Завтра аналитиком может быть DeepSeek или другая модель.

Аналитик может работать:

1. через командную строку;
2. через API.

Поэтому вход и выход аналитика должны быть структурными.

Аналитик не должен хранить логику только в свободном тексте.

## 47. Вход аналитика

Вход аналитика должен включать:

1. направление;
2. вариант запуска;
3. город;
4. бюджет клиента;
5. режим бизнес-плана;
6. факты;
7. источники;
8. цены;
9. расходы;
10. ограничения;
11. дату расчёта.

## 48. Выход аналитика

Выход аналитика должен включать:

1. статус;
2. расчёты;
3. выводы;
4. недостающие данные;
5. риски;
6. ссылки на факты;
7. уровень доверия;
8. дату;
9. версию расчёта.

## 49. Проверяющий

Проверяющий должен проверять:

1. есть ли источники;
2. свежие ли цены;
3. не смешаны ли факты и выводы;
4. есть ли скрытые допущения;
5. есть ли неподтверждённые числа;
6. возможен ли расчёт;
7. не обещается ли прибыль;
8. не обещается ли соцконтракт.
